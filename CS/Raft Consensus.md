## 등장 배경
Raft의 등장 이전에는 분산 시스템의 거장 Lesile Lamport에 의해 만들어진 Paxos가 대세를 이루었는데, 스탠포드 대학의 학생인 본인들이 Paxos를 이해하는데 거의 1년 가까이 걸릴 정도로 어려웠기 때문에 새로운 합의 알고리즘을 만들려고 했다고 함.

## 복제 상태 머신(Replicated State Machine)
합의 알고리즘은 대부분 복제 상태 머신을 구현하기 위해서 사용되는 수단. 블록체인도 마찬가지로 분산 시스템에서 각 노드가 동일한 상태를 가지는 것을 목표로 하기 때문에 복제 상태 머신의 한 종류라고 할 수 있음.  
복제 상태 머신에서는 다수의 노드가 클러스터를 구성하고 있는 상황에서 일부 장애가 발생하더라도 전체 시스템은 문제 없이 동작할 수 있도록 함. 이런 특징 덕분에 대규모 분산 시스템에서 다양한 종류의 장애 허용 문제를 해결하기 위해 사용되며 대표적으로 kafka에서 이용하는 Apache Zookeper와 쿠버네티스에서 이용하는 etcd 등이 있음.

### 구현 방식
Raft는 복제 로그(Replicated Log)를 구성해서 복제 상태 머신을 구현함. 복제 로그는 클러스터에 연결된 모든 노드에 대해서 사용자의 명령어를 동일한 순서로 저장하는 것을 목표로 함. 일관된 로그를 잘 복제하면 클러스터의 각 노드의 상태 머신(State Machine)이 명령어를 순차적으로 해석해서 동일한 상태를 만듦. 메시지는 결정론적 명령만을 수행하기 때문에 항상 동일한 상태가 만들어질 것을 보장.  
클라이언트는 합의 모듈(Consensus Module)에 로그 기록을 요청하고 이를 다른 서버와 통신해서 서로 다른 노드에 저장된 복제 로그가 최종 일관성을 가질 것을 보장함.

- 분산 시스템에서 신뢰할 수 있는(highly reliable)은 일부 장애가 발생하더라도 시스템은 동작하여 항상 신뢰하여 사용할 수 있는 환경을 말함.

### 복제 상태 머신은 다음의 속성을 만족해야 함.
- 안정성: non-Byzantine 조건에서 안정성을 갖춰야 함.(네트워크 딜레이, 분할, 패킷 손실, 중복 전송 등)
- 가용성: 다수의 서버가 동작할 수 있고 서로 통신이 가능한 상황이라면 모든 기능은 동작해야 함. 따라서 5개의 클러스터로 구성되어 있으면 최대 2개의 장애 허용성을 가짐. 각 서버는 일시적인 중단인 것으로 여겨지며 나중에 복구됨.(클러스터 탈퇴와 장애는 다름.)
- 로그의 일관성을 맞추기 위해 타이밍에 의존하지 말아야 함.(고장난 시계와 급격한 메시지 지연은 가용성 문제를 일으킬 수 있음.)
- 다수의 클러스터가 하나의 라운드에서 응답 했다면 바로 성공할 수 있어야 함. 소수의 느린 서버가 전체 시스템 성능에 영향을 미치면 안됨.

### 이해하기 쉬운 컨센서스 만들기
Raft는 기존에 이해하기 어려웠던 Paxos를 대체하기 위해 만들어졌음. 분할/정복을 이용. Raft는 합의 알고리즘을 크게 1. 리더 선출, 2. 로그 복제, 3. 안정성 보장이라는 3가지 문제로 나눠서 해결하고 이를 하나의 컨센서스 모듈로 만들기로 함.

### 리더 선출(Leader Election)
노드는 한 순간에 하나의 상태만을 가짐. 노드는 내부적으로 임기(Term) 제도를 운영하고 있음. 3대, 4대 대통령으로 부르듯이 임기도 1씩 증가하며 매 임기마다 하나의 리더를 선출함.
- 리더(Leader): 정상적인 상황에서 클러스터는 하나의 리더와 N-1개의 팔로워로 구성됨. 리더는 클라이언트의 모든 요청을 수신 받으며 로컬에 로그를 적재하고 모든 팔로워에게 전달함.
- 팔로워(Follower): 팔로워는 클라이언트로 받은 요청을 리더로 리다이렉트 하고, 리더의 요청은 수신하여 처리하는 수동적인 역할만 함.
- 후보(Candidate): 새로운 리더를 선출하기 위해 후보가 된 상태.

리더 노드는 주기적으로 heartbeat 메시지를 노드로 전파하는데, 팔로워 노드가 임의의 시간동안 리더로부터 메시지를 받지 못하면 연결에 문제가 있는 것으로 간주하고 두 가지 행동을 함.

1. 저장된 임기 번호를 1 증가하고 즉시, 새로운 선거를 진행.
2. 본인이 스스로 후보가 되어 자신에게 투표를 하고 다른 노드들에게 투표 요청. RequestVote 메시지를 보냄.

임기의 시작은 선거와 함께 시작함. 스스로 후보가 되어 선거를 시작하는 경우 발생하는 경우는 3가지. 1. 과반수의 투표를 받아 당선되거나 2. 다른 노드가 리더가 되는 경우 그리고, 3. 승자 없이 투표가 종료되는 경우. 2.의 경우는 본인이 제출한 임기(Term) 번호보다 높은 번호로 당선된 리더가 있으면 후보에서 팔로워로 상태를 변경하고 리더로 등록함. 3.은 운이 없게도 모든 노드가 스스로에게 셀프 투표하고 모든 노드에게 전파하는 경우 투표가 동률로 결렬되는 경우.

### 랜덤 타임아웃 제도
Raft에서는 3.의 경우가 적게 발생하도록, 선거의 타임아웃을 150~300ms 사이로 노드마다 랜덤하게 할당함. 저자들은 원래 초기에 노드 별로 우선순위를 두는 랭킹 시스템을 생각했었는데 이것 저것 해본 결과 랜덤 타임아웃 제도가 제일 설계가 쉬웠다고 함.

## 로그 복제(Log Replication)
Raft에서 로그는 위치 값, 임기 번호, 상태 변경 명령 세 가지로 구성된 엔트리 (Entry)의 집합. 동일한 index와 임기 번호가 같다면 같은 명령을 저장해야 하고, 이전에 저장된 모든 로그가 동일함을 보장함.

### 커밋 엔트리(committed entries)
로그 엔트리는 리더가 생성하고, 과반수 이상의 서버에 복제되면 커밋된 것으로 간주. 커밋할 때는 이전에 생성한 모든 로그까지 한꺼번에 커밋함. 한 번 커밋된 엔트리는 이후의 다음 임기의 리더들에게 반드시 포함될 것을 보장하는데, 이를 Leader Completeness라고 부름.  
실용적으로는, 커밋된 엔트리만이 상태 머신에서 이행되며 상태를 변경함. 즉, Raft에서는 전체 클러스터에 걸쳐서 동일한 인덱스에는 동일한 로그 명령어만이 상태 머신에서 실행됨을 보장해야 함.

### 로그 매칭(Log Matching Property)
만약 두 로그가 동일한 인덱스와 동일한 임기 번호를 가진다면 해당 인덱스까지의 모든 엔트리가 동일함을 보장하는 속성을 로그 매칭이라고 함. 리더는 새로운 엔트리를 다른 서버로 전파할 때 AppendEntries RPC를 호출하는데 이때 인자값으로 바로 이전 로그의 인덱스와 임기번호, 리더의 커밋 인덱스를 같이 넘김.  
이를 통해 일관성을 확인할 수 있는데, 만약 요청을 수신받은 팔로워가 본인의 로그에서 인덱스와 임기번호가 일치하는 엔트리가 없으면 요청을 거부함. 만약 일치하는게 있다면 성공 메시지를 리턴하는데, 성공 메시지를 받은 리더 입장에서는 본인의 로그와 팔로워의 로그가 일치함을 알 수 있음. 이 과정은 연역되기 때문에 0번 인덱스부터 시작해서 N번째까지 반복하면 메시지가 동일함을 알 수 있음.

### 로그의 일치성
각 서버의 로그는 다양한 상황 때문에 불일치 할 수 있음. 이러한 상황들에서 Raft는 팔로워의 로그를 리더의 로그로 덮어 씌우는 것으로 문제를 해결하는데, 특정 제약 조건이 붙으면 이 상황이 더 안전함. 팔로워의 상태를 맞추기 위해 리더는 팔로워와 동일한 로그를 가진 인덱스를 찾아서 이후 인덱스의 로그를 팔로워에서 모두 제거한 후 자신의 로그를 복제함.  
이 동작은 AppendedEntries RPC를 통해 이루어지는데, 이는 하나의 로그만을 추가함. 리더는 모든 팔로워에 대해 nextEntry 인덱스를 내부적으로 저장하고 있는데, 당선되는 경우에는 본인 로그의 최신 인덱스를 값으로 가지고 있다가 AppendEntries RPC를 보내보고, 만약 실패한다면 이 값을 1씩 감소시켜서 성공할 때까지 반복함.

## 안정성(Safety)
팔로워가 리더의 커밋 메시지를 수신받지 못하고 본인이 리더가 되어서 메시지를 덮어 씌우느 상황이 연출되어서 각 서버의 상태 머신이 서로 다른 메시지를 이행할 수 있음. 안정성 항목에서는 이런 상황을 방지하기 위해 취해지는 여러 방법을 소개함.

### 선거 제약(Election Restriciton)
모든 합의 알고리즘에서 리더는 최정적으로 모든 커밋된 로그를 저장해야 함. 일부 합의 알고리즘은 커밋된 로그를 가지고 있지 않아도 리더로 선출될 수 있기 때문에 팔로워들이 커밋 로그를 리더로 전송해주는 추가적인 매커니즘이 필요함. Raft는 이런 방식이 추가적인 복잡성을 야기한다고 해서 쉬운 방법을 택함.  
우선, 후보 노드가 당선되기 위해서는 클러스터 내 다수의 노드에게 연락해야 함. 이는 연락한 노드들 중 다수는 반드시 커밋된 로그를 가지고 있음을 의미함. 투표 요청(Request Vote) RPC에는 후보의 로그가 인자값으로 존재하는데, 투표자는 본인의 임기 번호가 더 높거나, 로그 인덱스가 더 큰 경우 해당 투표 요청을 거부함. 따라서, 모든 당선된 리더는 반드시 커밋된 로그를 가지고 있음을 보장함.

### 커밋 규칙(Commit Rules)
Raft에서는 이전 임기의 메시지가 단순히 과반수 이상 서버에 복제되었다고 커밋으로 간주하지 않고, 반드시 현재 임기의 메시지가 복제되어야지만, 커밋으로 간주함. 커밋은 상태 머신이 어떤 엔트리를 실행할 지 결정하는 값이기 때문에 중요함.

## 멤버쉽 변경(Membership Changes)
가장 단순한 방법은 모든 서버를 셧다운 시키고 서버를 추가한 다음, 실행하는 건데 이는 실용적으로 봤을 때는 쓸모가 없기 때문에 동적으로 멤버를 추가할 수 있어야 함.  
하지만, 분산 서버에서는 모든 설정을 한 순간에 변경할 수 없기 때문에 반드시 2명의 리더가 선출되는 상황이 연출될 수 있음.  
Raft에서는 이 문제를 해결하기 위해, 스스로 결합 합의(join consensus)라고 부르는 방법을 사용함. 이 방법의 기본 아이디어는 서버 별로 새로운 설정 정보로 전환하기까지 시간을 두는 것을 허용하는 것. 방법론적으로는 새로운 설정 정보를 로그 엔트리에 포함시키고 이것을 대다수 노드에 복제되어 커밋되고 나서야 새로운 설정 정보를 활용함. 이러한 결합 합의 방식에는 3가지 문제가 나타날 수 있음.  
1. 새롭게 참여한 서버가 아직 아무런 로그도 저장하지 못한 상황, 만약 이 서버가 바로 투표에 참여하면 절대 리더로 선출되지 못하기 때문에 Raft에서는 설정 변경 전에 투표권이 없는(Non-Voting) 멤버로 참여시켜서 먼저 동기화를 완료하고 결합 합의를 진행함.
2. 현재 리더가 새로운 설정 정보에는 포함되어 있지 않은 경우. 이 경우에 리더는 본인이 C_new 설정 정보가 담긴 엔트리를 커밋한 경우 스스로 팔로워 상태로 변경하고 사임함.
3. 새로운 설정에선 삭제된 멤버가 클러스터를 망칠 수 있다는 이슈가 있음. 우선 새 집단에서 제외되었기 때문에 heartbeat 메시지를 수신 받지 않음. 따라서, 스스로 후보 상태로 변경해서 선거를 진행하려고 하기 때문에 현재 리더가 팔로워 상태로 변경될 수 있음. Raft에서는 단순히 클러스터 내 노드들이 현재 자신이 리더가 존재한다고 믿는 상태라면 투표를 거부하여 이 문제를 해결함.

## 결론
성능과 관련된 항목은 새로운 리더가 선출되기까지 리더가 없이 대기하는 시간이 얼마나 짧은지를 선거 타임 아웃 시간 파라미터마다 보여줌.
