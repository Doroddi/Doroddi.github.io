## 웹 분산 시스템 설계 시의 고려 사항
확장성 있는 웹 사이트나 웹 애플리케이션을 만들고 관리한다는 것은 사용자들이 인터넷을 통해 원격지의 자원에 연결할 때, 자원이나 자원에 대한 접근 권한이 여러 개의 서버에 분산되어 있을 때를 말함.  
소규모 웹 사이트를 만들 때도 대규모 사이트를 설계할 때의 고려 사항과 여러 트레이드 오프에 대해 이해하고 있다면 좀 더 현명한 결정을 내릴 수 있게 될 것.  

대규모 웹 시스템을 설계할 때 고려해야 할 주요 사항  
- 가용성(Availability): 웹 사이트의 가용성은 많은 회사의 명성과 기능에 절대적으로 중요한 것. 항상 가용적이고 장애에 유연한 아키텍처를 가지는 것은 가장 기본적인 비즈니스 요구사항. 분산 시스템에서 높은 가용성을 얻기 위해서는 중요한 컴포넌트의 이중화, 실패가 발생했을 경웨 대한 빠른 복구 방법, 문제가 발생할 때 일부만으로 동작할 수 있게 전체에 장애가 발생하지 않게 하는 구성(graceful degradation)에 대한 고려가 필요.
- 성능(Performance): 대부분의 웹 사이트에서 성능은 매우 중요한 고려사항. 웹 사이트의 속도는 사용성, 만족도 뿐 아니라 수익 및 유지에 직접적으로 연관이 있는 검색 엔진의 랭킹에도 중요한 영향을 미침. 결과적으로 빠른 응답 시간과 낮은 레이턴시를 위해 최적화된 시스템을 만드는 것이 중요.  
- 신뢰성(Reliability): 항상 똑같은 요청에는 똑같은 결과를 제공해야 함. 시스템이 항상 정상적으로 동작해야 함. 데이터가 변하거나 업데이트되고 나면 업데이트된 새로운 데이터를 반환해야 함. 어떤 데이터가 시스템에 저장된 이후 사용자가 해당 데이터를 검색할 때 항상 그 결과가 반환된다는 것을 사용자들이 알게 할 필요가 있음.  
- 확장성(Scalability): 더 많은 부하를 처리할 수 있도록 처리량을 증가시키기 위해 필요한 노력. 시스템의 확장성이란 시스템의 여러 특징이나 기능/비기능 한계 상황으로 설명될 수 있음. 예를 들어 얼마나 많은 추가적인 트래픽을 처리할 수 있는지, 저장 공간을 추가하기가 얼마나 쉬운지, 얼마나 더 많은 트랜잭션을 처리할 수 있는지 등.  
- 관리성(Manageability): 쉽게 운용할 수 있는 시스템을 설계하는 것은 또 다른 중요한 고려 사항. 시스템의 관리성이란 운용(유지와 업데이트)의 확장성과 같은 말. 관리성이 좋아지려면 문제 발생 시 분석이 용이해야 하며 문제를 이해하기 쉬워야 함. 그리고 업데이트, 수정, 시스템 운용 자체가 쉬워야 함.  
- 비용(Cost): 비용은 중요한 요소. 하드웨어와 소프트웨어 비용을 포함하여 시스템을 배포하고 관리하는 비용 또한 고려해야 할 사항. 이러한 비용에는 시스템이 빌드하는 데 걸리는 시간, 시스템을 실행시키는 데 드는 운용 노력의 양, 모든 고려해야 할 사항에 대해서 필요한 교육 비용까지 포함됨. 시스템 소유에 필요한 모든 비용.

이러한 고려 사항들은 분산 웹 시스템을 설계할 때 판단 기준으로 사용할 수 있지만 어느 하나를 향상 시키는 것이 다른 하나의 하락을 가져올 수도 있음.

## 기초
‘서비스들’, ‘이중화’, ‘분할’, ‘예외 처리’는 거의 모든 대규모 웹 애플리케이션에 필요한 핵심 사항.

### 서비스들(Services)
확장성 있는 시스템을 설계할 때 각각의 명확한 인터페이스를 기반으로 기능별로 나누어 생각하는 것은 좋은 방법. 이러한 방식으로 설계하는 시스템을 SOA(Service-Oriented Architecture)라고 부름. SOA에서는 명확하게 기능별로 서비스를 구성함. 그리고 각각의 서비스는 다른 서비스와 상호 작용을 위해 다른 서비스에서 공개하는 API 형태인 추상화된 인터페이스를 사용.  
시스템을 상호 보완적인 서비스로 분할한다는 것은 시스템을 기능 단위로 분리시키는 것을 말함. 이러한 추상화는 서비스와 서비스가 처한 환경 그리고 서비스와 서비스 사용자 사이의 명확한 관계를 수립하는 데 도움이 됨. 이러한 명확한 기술은 문제를 분리시키는 데도 도움이 되지만, 각각을 독립적으로 확장 시키는 것에도 효과적임. 이런 의미에서 시스템에서의 SOA는 객체지향 프로그래밍과 유사.  
서비스가 굉장히 많이 사용된다라고 가정할 때 다운로드와 업로드의 속도가 똑같다고 가정해도(실제로는 3:1 정도의 비율), ‘읽기’는 캐시의 도움을 받을 수 있지만 ‘쓰기’ 요청은 결과적으로 디스크까지 도달해야 함. 심지어 모든 데이터가 메모리나 SSD에 있는 경우에도 데이터베이스 쓰기는 읽기보다 느림.  
이러한 디자인의 또 다른 잠재적 문제는 Apache나 lighthttpd 같은 웹 서버는 동시 커넥션 수에 상한선이 있다는 것. 읽기는 비동기일 수 있기 때문에 성능 최적화 가능. 웹 서버의 초당 읽기 요청 처리 수는 보통 최대 커넥션 수보다 많음.  
한편 쓰기의 경우에는 업로드 동안 연결을 열어 놓은 상태로 유지해야 함.  
이러한 병목 현상에 대한 대처로 읽기와 쓰기를 각각의 서비스로 분리하는 것은 좋은 방법.  
이 방법은 읽기와 쓰기를 각각 독립적으로 확장할 수 있게 하고 시스템의 각 부분이 어ᄄᅠᇂ게 돌아가고 있는지 명확히 확인하는 데 도움이 됨. 결과적으로 읽기가 느린 현상이 발생할 때 문제를 해결하고 확장하는 것을 쉽게 함.  
이러한 시스템 아키텍처에 정답이란 것은 없지만, 시스템이 요구하는 것을 결정하고, 여러 대안을 벤치 마킹하고, 시스템이 어떤 경우에 문제가 생기는지 이해하고, 그리고 문제가 발생했을 때에 대한 확실한 계획을 가지는 것이 필요함.

### 이중화(Redudancy)
장애에 대처하기 위한 웹 아키텍처에는 데이터와 서버에 대한 이중화가 고려되어야 함. 예를 들어 한 파일이 어느 한 서버에만 저장되어 있으면 해당 서버에 장애가 발생할 때 그 파일을 잃어버리게 됨. 이를 방지하는 보편적인 대처법은 여러 서버에 데이터를 복제해 두는 것.  
같은 원칙이 서비스에도 적용됨. 애플리케이션에 중요한 핵심 기능이 있다면 같은 기능을 하는 여러 개가 동시에 동작하도록 하는 것이 필요.  
시스템을 이중화하는 것은 단일 고장점(single point of failure)을 없애고, 장애 발생 시에도 백업하게 할 수 있거나 시스템이 계속 동작할 수 있게 함.  
서비스를 이중화할 때 중요한 것은 Shared Nothing 아키텍처를 만드는 것. 이 아키텍처에서는 각각의 노드는 상태나 작업을 관리하는 중앙부 없이 독립적으로 동작 가능함. 이러한 구조는 시스템이 확장성을 가지고자 할 때 매우 유용함. 중요한 것은 시스템이 단일 고장점을 갖지 않게 된다는 것. 따라서 장애에 좀 더 잘 대처할 수 있게 됨.

### 파티션(Partitions)
하나의 서버에서 감당할 수 없는 많은 데이터가 있거나 연산을 위해 많은 컴퓨팅 자원이 필요하게 되어 성능이 떨어지게 되는 경우가 있을 수 있음. 이러한 문제를 해결하기 위해서는 두 가지 선택이 있는데 하나는 수직적 확장이고, 다른 하나는 수평적 확장임.  
수직적 확장은 개개의 서버에 더 많은 자원을 추가하는 것을 말함. 서버에 하드 디스크를 추가하거나 더 빠른 계산 성능을 위해 더 빠른 CPU와 큰 용량의 메모리를 추가하는 것 역시 마찬가지. 즉, 수직적 확장은 각 자원의 처리 능력 향상을 말함.  
반면 수평적 확장이란 노드를 추가하는 것. 데이터가 많을 경우에 부분 데이터를 저장할 수 있는 노드를 추가하는 것. 많은 연산을 필요로 하는 경우에는 연산을 분리하여 추가한 노드에서 작업이 이루어지도록 함. 수평적 확장의 장점을 모두 취하기 위해서는 시스템 아키텍처의 고유한 설계 원칙들을 따라야 함. 그렇지 않으면 기능 단위를 수정하거나 분리하는 것이 굉장히 불편한 일이 되어 버릴 수도 있음.  
수평적 확장을 하는 가장 보편적인 방법은 서비스를 파티션이나 샤드 단위로 분할하는 것. 파티션은 기능별 논리 집합으로 분산될 수 있음. 이러한 파티션은 특정 사용자나 데이터의 지리적인 위치에 따라 만들어질 수 있고, 혹은 무료 사용자냐 유료 사용자냐와 같은 기준에 따라 만들어질 수 도 있음. 이러한 형태의 장점은 증설한 것을 바탕으로 서비스나 데이터 저장소를 제공할 수 있음.  
여러 서버에 데이터나 기능을 분산시키는 것에는 기술적인 도전이 있음. 여러 핵심 이슈 wd 하나는 데이터 로컬리티인데 연산하려는 데이터가 가까이 위치해 있을수록 시스템의 성능은 향상됨. 따라서 필요한 데이터를 여러 서버에 분산시키는 것은 로컬에 있지 않을 수 있는 데이터를 얻기 위해 비용이 높은 네트워크를 이용한 읽기가 발생할 수 있어 잠재적인 성능 문제가 발생할 수 있음.  
또 다른 잠재적 이슈는 비정합성. 공유된 자원으로부터 읽기와 쓰기를 하는 서로 다른 서비스가 있다고 가정했을 때 여기서는 경합 조건이 발생할 가능성이 있음. 어떠한 데이터가 업데이트되려할 때, 읽기 요청이 업데이트 요청보다 먼저 발생했다면 해당 데이터는 비정합성 상태가 됨.  
데이터를 파티셔닝하는 것에는 난관이 있지만 파티셔닝은 각각의 문제(데이터, 로드, 사용 패턴 등)를 관리할 수 있는 조그마한 단위로 분리시킬 수 있게 함. 이러한 점은 확장성과 관리성에 도움을 주지만 위험이 없지는 않음.  

## 빠르고 확장성 있는 데이터 액세스를 위한 빌딩 블록
Internet-App Server-Database Server로 구성된 간단한 형태의 웹 애플리케이션을 많은 사용자가 사용하게 되면 두 가지 기술적인 문제에 직면하게 됨. 하나는 애플리케이션 서버에 대한 데이터 액세스를 확장성 있게 하는 것, 다른 하나는 데이터베이스에 대한 데이터 액세스를 확장성 있게 하는 것. 확장성이 있도록 설계된 애플리케이션에서는 애플리케이션 서버(혹은 웹 서버)는 최소화되고 때로는 shared-nothing 아키텍처를 가짐. 이 때문에 애플리케이션 서버 레이어는 수평적 확장이 가능해지게 됨. 그렇기 때문에 데이터베이스 레이어를 확장성 있게 만들 숙제만이 남게 됨.  
많은 데이터가 있을 때, 우리는 데이터의 빠르고 쉬운 액세스를 원함.  
모든 데이터를 메모리에 저장하지 않으면서도 빠른 액세스가 가능하도록 하는 것은 매우 어려운 과제인데, 여기서 성능에 가장 영향을 많이 미치는 것은 디스크 I/O임. 디스크에서 데이터를 읽는 것은 메모리에서 데이터를 읽는 것보다 훨씬 더 느림.

### 캐시
캐시는 최근에 요청받은 데이터는 다시 요청받을 확률이 높다는 지역성의 원리(locality of reference)에 기반한 방법. 캐시는 하드웨어, 운영체제, 웹 브라우저, 웹 애플리케이션 등 다양한 곳에서 사용하고 있음. 캐시란 매우 짧은 시간 동안 유지되는 메모리와 같은 것. 캐시 용량은 매우 제한적이지만, 통상적으로 원래의 데이터 저장소보다는 매우 빠르고 자주 액세스되는 데이터를 보유하고 있음. 캐시는 아키텍처의 모든 단계에 위치할 수 있지만, 프런트엔드와 가까운 곳에 위치하는 경우가 많음. 왜냐하면 보통 캐시는 서비스의 백 엔드까지 가는 시간적인 비용을 줄이기 위해 사용하는 경우가 많기 때문.  
캐시를 요청 노드에 배치하는 것은 응답 데이터를 로컬 저장 공간에서 가져올 수 있게 함. 매번 요청은 서비스로 보내지고, 요청 노드에 데이터가 존재하면 그 노드는 재빠르게 로컬에서 캐싱된 데이털 보냄. 만약 캐시에 데이터가 없다면 요청 노드는 디스크에서 데이터를 질ㅇ릐할 것. 여기서 캐시는 요청 노드의 메모리에 있을 수도 있고 요청 노드의 로컬 디스크에 존재할 수도 있음(네트워크 스토리지를 사용하는 것보단 빠름).  
이러한 요청 노드를 여러 개로 확장하면 각 노드가 각각의 캐시를 가질 수 있게 됨. 그러나 만약 로드 밸런서가 임의로 요청을 분산시키면, 같은 요청이 다른 노드로 가게 될 수도 있음. 이는 곧, 캐시 미스로 이어짐. 캐시 미스를 줄이면서 여러 개의 캐시를 사용하기 위해 사용하는 방법이 전역 캐시와 분산 캐시.

### 전역 캐시(Global Cache)
전역 캐시는 모든 노드가 오직 하나의 캐시 공간만을 사용함. 전역 캐시는 서버나 어떤 종류의 파일 저장소를 추가해도 잘 동작하고, 원래의 저장소보다 빠르며 모든 요청 레이어 노드에서 접근이 가능.  
요청 노드에서 각각의 요청은 로컬에 캐시를 가지고 있는 것과 마찬가지로 글로벌 캐시에 데이터를 질의함. 이러한 종류의 캐시 사용은 클라이언트의 개수나 요청 개수가 급격하게 증가하면 하나의 캐시가 그 요청을 감당하지 못할 수도 있기 때문에 복잡해짐. 하지만 이러한 아키텍처가 특정한 상황에서는 매우 유용함(특화된 하드웨어를 써서 전역 캐시를 빠르게 만들거나, 캐시가 필요한 데이터의 양이 고정된 일정량일 때).  
전역 캐시에는 두 가지 일반적인 방식이 있음.

1. 요청 노드는 오직 캐시에만 데이터를 질의하고, 전역 캐시는 요청받은 데이터를 자기 자신에서 찾을 수 없을 때, 캐시 스스로가 저장 공간에 데이터를 질의하여 요청 노드에 데이터를 전달하도록 하는 방식.  
2. 요청 노드가 전역 캐시에서 데이터를 질의하여 데이터가 없을 확인하였을 때는 직접 스토리지에 질의하여 데이터를 가져오는 방식.  

전역캐시를 사용하는 대부분의 애플리케이션은 같은 요청이 여러 요청 노드로부터 발생하는 것을 막기 위해 캐시 스스로가 데이터 추출과 조회를 직접하는 1번을 사용함.  
그러나 2번이 더 유용할 때도 있는데, 큰 크기의 파일 제공을 위하여 캐시를 사용하는 경우에, 낮은 캐시 히트가 발생하면 전반적인 캐시 미스가 증가하게 됨. 이 경우에는 자주 사용되는 데이터만 캐시에 위치하게 하는 것이 도움이 됨. 또 정적 파일을 캐시에 저장하는 경우. 이 경우에는 정적 파일은 절대 캐시에서 지워지지 않음(레이턴시 에대한 애플리케이션 요구사항 때문. 많은 데이터 처리를 위하여 데이터 일부는 빠르게 전송될 필요가 있음. 이런 경우에 캐시 자체보다는 애플리케이션 로직이 캐시 추출이나 핫스팟 관리를 하는 것이 좋음.).

### 분산 캐시(Distributed Cache)
분산 캐시는 각각의 노드가 캐시 데이터를 갖는 방식. 일반적으로 분ㄴ산 캐시는 consistent hashing 함수를 사용함. 따라서 요청 노드가 어떤 특정한 데이터 조각을 찾으려 할 때 해시 함수를 이용해 분산 캐시 내의 어디에서 데이터를 찾을 수 있는지 알 수 있음. 각각의 노드는 조그마한 캐시를 가지고 있음. 그리고 요청이 들어오면 원본 저장 공간으로 요청을 보내기 전에 다른 노드에 요청을 보냄. 분산 캐시의 이런 점 때문에 요청 풀에 노드를 추가하면 전체 캐시 크기를 증가시킬 수 있음.  
분산 캐시의 단점은 장애가 발생한 노드를 처리하는 방법이 필요하다는 것. 이는 다른 노드에 여러 개의 복제본을 가지는 방법으로 해결하기도 하는데 이런 방식을 사용하면 문제 노드를 처리하기 위한 로직이 복잡해지기 십상임. 요청 레이어에 새로운 노드를 추가하거나 제거하려 할 때 특히 그럼. 물론 노드가 사라지고 캐시의 일부분이 분실되더라도 원본 데이터에 요청함으로ㅆ 필요한 데이터를 가져올 수 있음. 그렇기에 분산 캐시에 장애가 발생한다고 해서 총체적인 장애가 발생하는 것은 아님.  

캐시의 장점은 캐시가 올바르게만 구현되어 있다면 시스템을 더욱 빠르게 만들 수 있다는 것. 캐시를 이용해 더욱 더 많은 요청을 이전보다 더 빠르게 처리하게 할 수도 있음. 그러나 이러한 캐시 시스템에는 일반적으로 값 비싼 메모리와 같은 추가적인 저장 공간을 유지하기 위한 비용 문제가 항상 따름. 캐시는 빠른 처리를 가능하게 하는 굉장히 훌륭한 방법. 또한 캐시가 없다면 총체적인 성능 저하가 발생할 수 있는 심한 부하가 상황에서도, 캐시가 있다면 완전하게 시스템의 기능들이 동작하게 하도록 할 것임.

### 프락시
기본적으로 프락시 서버라 하면 클라이언트의 요청을 백엔드 서버에 전달하는 역할을 하는 중간의 하드웨어 혹은 소프트웨어를 의미함. 프락시는 요청을 필터링, 로깅, 변환(헤더에 속성 더하고/빼고, 암호화/복호화, 압축)하는데 사용함.  
프락시는 여러 서버에서 오는 요청을 받아 정리하여, 전체 시스템 관점에서 트래픽을 최적화시키는데도 도움이 됨. 데이터 액세스를 빠르게 하기 위하여 프락시가 제공하는 방법 중 하나로 Collapsed Forwarding이라 부르는 것이 있는데, 같거나 비슷한 요청들을 모아 단 하나의 요청을 만들어 내는 것을 말함.  
여러 개의 노드가 같은 데이터를 요청한다고 했을 때, 요청 데이터가 캐시에 없다면, 프락시를 지나가게 되는 똑같은 요청들은 하나의 요청으로 바뀔 것이고 단 한 번의 읽기 연산이 발생함. 요청을 그룹화하는데 드는 시간 때문에 각각의 요청에는 더 많은 레이턴시가 발생할 수도 있지만 부하가 높은 상황에서는 성능이 향상될 것임. 특히 똑같은 데이터가 반복적으로 읽힐 때. 이것은 캐시와 비슷하지만, 캐시가 데이터나 문서를 저장하는 것과는 다름. 프락시는 여러 클라이언트가 원하는 문서를 제공하기 위해 요청이나 콜을 최적화시키는 방법임.  
프락시를 사용하는 다른 방법으로는 공간적으로 가까운 데이터에 대한 요청을 묶어주는 것이 있음. 이러한 전략은 요청의 데이터 로컬리티를 최대화하여, 요청 지연을 줄일 수 있음. 프락시는 여러 번의 요청을 한 번에 처리하기 때문에 높은 로드 상황이나 캐시 사용이 제한적인 상황에서 특히 유용함.  
프락시와 캐시를 함께 사용하는 것은 무의미하지만, 같이 사용하게 될 때에는 캐시를 프락시 앞에 두는 것이 최선임. 

### 인덱스
인덱스를 사용하게 되면 데이터 양이 증가할 때 쓰기가 느려짐. 왜냐하면 쓰기를 할 때에는 데이터 기록과 아울러 빠른 읽기를 위해 인덱스를 업데이트해야 하기 때문.  
일반적인 관게형 데이터베이스에서처럼 이러한 개념이 많은 데이터를 다룰 때에도 적용됨. 인덱스를 이용할 때는 사용자들이 어떠한 식으로 데이터에 접근할지에 대한 충분한 고려가 필요함. 큰 규모의 데이터에서 작은 데이터를 찾을 때, 데이터 액세스를 최적화하기 위해 인덱스는 필수적임.  
인덱스는 목차와 같이 데이터가 어디에 위치하는지 알려주는 역할을 함. 이러한 색인은 보통은 메모리에 있거나, 들어오는 클라이언트 요청과 굉장히 가까운 곳에 위치해 있음. BerkeleyDB와 트리 형태의 구조는 이러한 정렬된 리스트를 저장하고 색인을 사용하는 이상적이고 보편적인 방법이라 할 수 있음.  
때때로 맵의 형태를 가진 여러 개의 레이어로 이루어진 인덱스도 있음. 이런 인덱스에서는 특정한 데이터를 얻을 때까지 한 위치에서 데이터가 있는 다음 위치로 이동할 수 있게 함.  
인덱스는 같은 데이터를 다른 여러 개의 뷰로 만드는데 사용할 수 있음. 특히 많은 데이터를 다룰 때 추가적인 데이터 복사본을 사용하여 재정렬하지 않고, 다른 필터를 정의하고 정렬할 수 있다는 것은 인덱스의 엄청난 장점.  
중간 인덱스는(intermediate indexes)는 하나의 큰 인버티드 인덱스를 사용하는 것보다 적은 공간을 사용할 수 있게 함.  
규모가 큰 시스템에서 중간 인덱스는 매우 중요함. 데이터가 많다면 압축이 된다 하더라도 인덱스 크기는 꽤 클 수 있고 저장하는 것에도 그만큼의 비용이 필요하기 때문.  
중간 인덱스를 만들고 데이터를 더 작은 섹션으로 나타내는 것은 많은 데이터를 다루기 쉽게 해줌. 데이터는 많은 서버에 퍼져 있지만 인덱스를 이용하기 때문에 빠르게 접근 가능.

### 로드 밸런서(Load Balancers)
로드 밸런서는 어떤 아키텍처에서든 중요함. 로드 밸런서는 서비스 요청을 여러 노드에게 분배하는 일을 함. 즉, 로드 밸런서를 이용하여 하나의 시스템에서 여러 개의 노드가 투명하게 서비스 안에서 똑같은 기능을 수행할 수 있게 함. 로드 밸런서의 주 목적은 동시에 오는 수많은 커넥션을 처리하고 해당 커넥션이 요청 노드 중의 하나로 전달될 수 있게 하는 것. 그리고 단지 노드를 추가하는 것만으로 서비스가 확장성을 가질 수 있도록 함.  
로드 밸런서에서 서비스 요청을 처리하는 방법에는 다양한 알고리즘이 있는데, 랜덤, 라운드 로빈, CPU나 메모리 사용률 등과 같은 특정 범주에 따라 노드를 선택하는 등의 방법이 있음. 로드 밸러서는 소프트웨어로 구현될 수도 있고 하드웨어 제품이 될 수도 있음.  
분산 시스템에서 로드 밸런서는 들어오는 모든 요청이 거쳐가는 시스템의 프런트엔드에 위치하곤 함.  
프락시처럼 어떤 로드 밸런서는 요청의 종류를 파악하고 해당 요청을 처리할 수 있는 노드에 전달하는 기능을 가지고 있음(이러한 형태를 리버스 프락시라고 부름).  
로드 밸런서를 사용할 때 어려운 문제 중 하나는 세션 데이터를 관리하는 것. 한 웹 서비스에서 사용자의 정보를 유지해야 하는데 방문 때마다 다른 세션을 사용한다면 유저의 정보를 일관성 있게 유지할 수 없게 됨. 이러한 문제를 해결하는 한 가지 방법은 세션을 고정하도록(session sticky) 하는 것. 이 방법으로 사용자의 요청이 전달될 노드를 고정시킬 수 있음. 그러나 이 방식은 자동 절체와 같은 신뢰성과 관련된 기능을 사용할 수 없게 함. 
단지 몇 개의 노드만 있을 뿐이라면 라운드 로빈 DNS와 같은 방식이 합리적일 것. 로드 밸런서 자체의 비용이 높기도 하지만 불필요한 복잡함을 증가시킬 수도 있기 때문. 대규모의 시스템에서는 랜덤이나 라운드 로빈같은 단순한 방식이 물론이고 시스템 사용률이나 처리량을 고려한 복잡한 방식을 사용하는 다양한 알고리즘과 스케쥴링을 사용하고 있음. 이러한 로드 밸런싱 알고리즘은 모두 네트워크 트래픽과 분산 요청을 제어하면서 자동 절체나 이상 노드 제거(응답이 없을 때)와 같은 신뢰성 관련한 기능을 제공하기도 함. 그러나 이러한 향상된 기능이 장애 분석을 방해하기도 함. 이를 위해 시스템의 전체적인 상황을 파악할 수 있는 모니터링이 중요함.  
로드 밸런서는 시스템 용량을 확장시키는 쉬운 방법. 노드에 대한 헬스체크 기능을 제공하기도 하고 반응이 없거나 과부화 상태에 있는 노드를 풀에서 제거하여 시스템 이중화의 장점을 이용할 수 있게 함.

### 큐(Queues)
시스템이 확장성 있도록 설계하려면 쓰기에 대한 고려 또한 필요함. 복잡한 시스템에서의 쓰기는 전체 수행 시간을 예상할 수 없을 정도로 복잡한 것이 되고는 함. 데이터가 여러 곳에 분산된 서버나 인덱스에 쓰여야 하고 당시의 시스템 부하 상태가 높다면 쓰기 연산은 매우 오랜 시간이 걸리는데 이럴 때 시스템의 성능과 가용성을 얻기 위해서 사용하는 보편적인 방법은 큐를 사용하는 것.  
동기적인 요청은 클라이언트의 성능을 심각하게 저하시킴. 왜냐하면 클라이언트는 요청에 대한 응답을 받기 전까지 아무런 일도 수행하지 않고 기다리기 때문. 시스템의 로드를 줄이기 위해서 서버를 추가한다고 해서 이와 같은 문제가 해결되지 않음. 또한 클라이언트의 성능을 최대화시키기 위해 로드 밸런싱을 한다는 것도 굉장히 어려운 문제임. 이러한 문제를 효과적으로 해결하기 위해서는 클라이언트 요청과 서비스를 처리하기 위해서 처리되는 일 사이에 추상화가 필요함.  
이에 대한 해답은 큐. 처리해야 할 일이 인입되면 그것은 큐에 쌓이고, 워커가 일을 처리할 수 있는 상황이 되면 워커 자신이 할 일을 큐에서 꺼내어 처리함. 클라이언트는 큐로 작업 요청을 보내고 난 다음 그 결과를 기다릴 필요가 없음. 대신 큐에 요청이 잘 쌓였다는 응답만 받음. 이 응답이 나중에 클라이언트가 받게 될 결과에 대한 참조 값으로 이용됨.  
큐의 장점은 클라이언트가 비동기 방식으로 동작할 수 있게 한다는 데 있음. 클라이언트의 요청과 그것에 대한 응답 사이에 전략적 추상화를 제공하는 것. 반면 동기적인 시스템에서는 요청과 응답의 차이가 없기 때문에 각각 분리되어 관리될 수 없음. 비동기 방식에서는 클라이언트 작업을 요청하고 서비스는 요청을 잘 받았다는 ACK를 해당 클라이언트에 전해 줌. 그 다음 클라이언트는 결과를 받을 때까지 주기적으로 작업의 상태를 체크하다가, 결과 값이 생성되었다는 것을 알게 되면 결과 값을 요청하여 받음. 클라이언트는 비동기적인 요청을 기다리는 동안 다른 일들을 처리하는 것이 가능. 심지어 또 다른 비동기 요청도 가능. 비동기 방식은 큐와 메시지가 분산 시스템에서 어떻게 이용되고 있는지를 잘 보여줌.  
큐는 서비스의 정지와 장애에 대비하는 보호 장치를 제공함. 일시적인 서버 장애 때문에 처리되지 않은 요청을 다시 보내는 굉장히 견고한 큐를 만드는 것은 꽤 쉬운 편. 그리고 서비스의 장애 상황을 직접 클라이언트에서 처리하게 하는 것보다 큐를 사용하는 것이 QoS(quality-of-service) 측면에서 더 바람직함.  
규모가 큰 분산 시스템에서 서로 다른 부분들끼리 분산 통신을 하는데 있어 큐는 필수적인 것이라 할 수 있으며 큐를 구현하기 위한 다양한 방법들이 있음.
