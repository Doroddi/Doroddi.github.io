# 1장. 소개 및 개요

## DBMS 구조  
클라이언트 요청(쿼리) -> [트랜스포트 서브시스템] -> [쿼리 프로세서] -> [실행 엔진] -> 로컬 쿼리 -> [스토리지 엔진]  

## 스토리지 엔진
- 트랜잭션 매니저: 트랜잭션 스케줄링, 논리적 일관성 보장
- 잠금 매니저: 잠금 제어, 동시 수행 작업에 대한 물리적 데이터 무결성 침해 제어  
(위 두 가지는 동시성 제어 -> 논리적 및 물리적 데이터 무결성보장 및 동시 수행 작업의 효율적인 수행 담당.)
- 액세스 메소드: 디스크에 저장된 데이터에 대한 접근 및 저장방식 정의. 힙 파일, B-트리 or LSM 트리 등의 자료 구조 사용.
- 버퍼 매니저: 데이터 페이지를 메모리에 캐시.
- 복구 매니저: 로그 유지 관리, 장애 발생 시 시스템 복구.

## 인메모리 DBMS
메모리(RAM)에 대부분의 데이터 저장, 디스크는 복구와 로그 저장 용도.  
디스크 기반 DBMS -> 데이터를 디스크에 저장, 메모리는 캐시 또는 임시 저장 용도.

### 장점
- 메모리는 디스크보다 훨씬 더 빠르게 데이터 접근.  
- 낮은 데이터 접근 비용.  
- 세밀한 접근 단위.
- 메모리 제어가 디스크 제어보다 프로그래밍적으로 더 간단함.
### 단점
- 비쌈.
- RAM의 휘발성(데이터 손실).
- 때문에 디스크가 메모리보다 유지관리 측면에서 더 간단하고 비용이 낮음.

인메모리 DBMS의 데이터 지속성을 보장하고 손실을 방지하기 위해 데이터를 디스크에 백업함.  
인메모리 시스템에서는 백업본을 유지하는데 백업본은 디스크 기반 자료 구조에 순서대로 저장.  
수정 내용은 비동기적으로 갱신(클라이언트 요청과 독립적으로 실행), I/O 작업 최소화를 위해 배치 단위로 백업, 데이터 복구 시 백업본과 로그를 기반으로 데이터 재구성.  

디스크 기반 DBMS는 디스크 접근에 특화된 특수한 자료 구조를 사용. -> 넓고 낮은 트리.  

## 로우형 데이터 레이아웃
데이터 레코드를 로우 형식으로 저장.  
여러 필드의 값을 고유 식별 키로 구분할수 있는 레코드 형식에 적합.  
한 개의 로우씩 접근하는 경우에 적합, 공간 지역성 극대화.  
특정 사용자의 모든 정보를 읽을 때는 효율적이지만 여러 사용자의 특정 필드를 읽을 때는 비효율적.

## 칼럼형 데이터 레이아웃
특정 칼럼 데이터의 추세와 평균 등을 계산하는 집계 분석 작업에 적합.  
조인과 필터링, 다중 로우 집계 등을위해 튜플을 재구성하려면 칼럼 사이의 관계를 정의하는 메타데이터가 필요.  
따라서 각 값마다 중복 저장된 키로 인해 데이터가 증가.

같은 칼럼의 여러 값을 한 번에 읽으면 캐시 활용도와 처리 효율성이 높아짐.  
자료형별로 저장하면 압축률도 증가.

데이터를 레코드 단위로 접근하고 일반 쿼리와 범위 스캔 요청이 많으면 로우형 DBMS가 적합.  
많은 로우를 스캔하거나 일부 칼럼에 대한 집계 작업이 많다면 칼럼형 DBMS가 적합.

## 와이드 칼럼 스토어
데이터를 다차원 맵으로 표현, 여러칼럼을 칼럼 패밀리 단위로 저장. 칼럼 패밀리의 데이터는 로우 형식으로 저장.  

## 데이터 파일과 인덱스 파일
- 저장 효율성: 데이터 레코드의 저장 오버헤드를 최소화하는 방식으로 파일을 구성할 수 있음.
- 접근 효율성: 최소한의 단계로 원하는 레코드를 찾을 수 있음.
- 갱신 효율성: 디스크 쓰기를 최소화하는 방식으로 레코드를 갱신.
데이터베이스 시스템은 데이터 파일과 인덱스 파일을 분리.
데이터 파일에는 데이터 레코드를 저장, 인덱스 파일에는 레코드에 대한 메타데이터를 저장하고 이를 사용해 데이터 파일에서의 레코드 위치를 찾을 수 있음.
새로운 레코드와 업데이트된 레코드는 키-값 쌍의 형식으로 저장함. 대부분의 최신 데이터베이스 시스템은 데이터를 즉시 페이지에서 삭제하지 않고 키와 타임스탬프 등의 삭제 관련 메타데이터를 저장한 삭제 마커를 사용하여 수정되거나 삭제 마커로 가려진 레코드는 가비지 컬렉션 중에 최신 레코드로 갱신되며 기존값은 삭제.

### 데이터 파일
인덱스 구조형 테이블, 힙 구조형 테이블 또는 해시 구조형 테이블을 기반으로 함.  
힙 파일은 레코드를 특정 순서를 따르지 않고 대체로 삽입 순서대로 저장함. 그러므로 새로운 페이지가 추가돼도 파일을 재구성하지 않아도 됨. 대신 데이터 검색 시 데이터의 실제 위치를 가리키는 인덱스 필요.  
해시 파일은 레코드를 각 키의 해시 값에 해당하는 버킷에 저장. 버킷 내 레코드는 삽입 순서대로 저장하거나 키 순서로 정렬하면 조회 속도를 향상 시킬 수 있음.
인덱스 구조형 테이블은 인덱스에 실제 데이터 레코드를 저장. 데이터는 키 순서로 정렬되기 때문에 IOT의 범위 스캔은 실제 값을 순서대로 읽으면서 비교. 인덱스에 데이터 레코드를 저장하면 디스크 탐색 횟수를 최소 1회로 줄일 수 있음.  
실제 데이터 레코드가 다른 파일에 저장돼 있으면 인덱스 파일에 레코드 식별자와 레코드의 위치를 저장해야 함.(데이터 파일에서 데이터의 위치를 나타내는 오프셋을 저장하거나 해시 파일의 경우 버킷 ID를 저장.)

### 인덱스 파일
디스크에 저장된 데이터 레코드를 효율적으로 검색할 수 있는 자료 구조.  
프라이머리 파일에 대한 인덱스 -> 기본 인덱스. 일반적으로 기본 인덱스는 기본 키 또는 기본 키 역할을 할 수 있는 여러 키의 조합에 대한 인덱스. 다른 인덱스는 보조 인덱스.  
보조 인덱스는 데이터 레코드를 직접 가리키거나 해당 레코드의 기본 키를 저장. 여러 보조 인덱스가 같은 레코드를 가리킬 수 있고, 하나의 레코드는 여러 다른 필드로 식별될 수 있으며 다양한 인덱스를 사용해 검색할 수 있음. 기본 인덱스는 키별로 하나의 레코드만 가리키는 반면, 보조 인덱스는 키별로 여러 레코드를 가리킬 수 있음.  
실제 데이터 레코드 정렬 순서와 검색 키의 정렬 순서가 같은 인데스를 클러스터 형 인덱스. 반대는 비클러스터형 인덱스. 기본 인덱스는 대부분 클러스터형 인덱스, 보조 인덱스는 비클러스터형 인덱스.  
대부분의 데이터베이스 시스템은 데이터 레코드를 식별할 수 있는 칼럼의 집합을 내부 키로 사용. 기본 키를 설정하지 않은 경우 내부적으로 기본 키를 자동으로 생성.

## 기본 인덱스를 통한 간접 참조
데이터를 직접 참조하면 디스크 탐색 오버헤드가 줄어듦. 대신 레코드를 갱신하거나 위치를 변경할 때마다 포인터를 수정해야 하는 오버헤드가 있음. 기본 인덱스를 통해 간접 참조하면 포인터 갱신 비용이 줄어들지만 레코드 위치를 찾는 과정 추가.  

## 버퍼링과 불변성, 순서화
- 버퍼링  
  데이터를 디스크에 쓰기 전에 일부를 메모리에 저장하는 것을 의미. 모든 디스크 기반 자료 구조에서는 버퍼를 어느 정도 사용.
- 가변성  
  파일 일부를 읽고 갱신한 뒤에 똑같은 자리에 다시 쓸지에 대한 여부를 나타내는 속성. 불변 구조에서는 한 번 쓴 파일 내용은 고칠 수 없고 파일 끝에 내용을 추가하는 추가 전용 구조.
- 순서화  
  디스크 페이지에 데이터 레코드를 키 순서로 저장하는 것을 의미. 정렬 순서상 인접한 키는 디스크의 연속된 세그먼트에 저장. 순서화는 특정 데이터 레코드 검색뿐만 아니라 효율적인 범위 스캔에 매우 중요한 속성. 반면 데이터를 임의의 순서로 저장하면 쓰기 시간 최적화.

# 2장. B-트리 개요

## 이진 탐색 트리
정렬된 인메모리 자료 구조, 키와 두 개의 자식 포인터가 저장된 여러 노드로 구성됨.  
각 노드의 키는 왼쪽 서브트리의 모든 노드 키보다 크고 오른쪽 서브트리의 모든 키보다 작음.  

## 트리 밸런싱
균형 트리란 노드 개수가 N일 때 높이가 logN이고 두 서브트리의 높이 차이가 최대 1인 트리.  
균형 트리 탐색 시간 복잡도 -> O(logN). 불균형 트리 탐색 시간 복잡도 -> O(N).  
새로운 노드 추가 시 트리의 균형을 유지해야 함. -> 노드 삽입으로 인해 트리의 균형이 깨진다면 가운데 노드를 중심으로 회전함.  

## 디스크 기반 스토리지용 트리
트리의 팬아웃(노드가 가질 수 있는 최대 자식 노드 개수)이 낮기 때문에 트리 밸런싱과 노드 재배치, 포인터 갱신이 자주 발생. 따라서 BST는 높은 트리 유지 비용 때문에 디스크 기반 자료 구조로는 적합하지 않음.  
BST를 디스크에서 제어하면 발생하는 문제.  
- 지역성: 새로운 노드와 부모 노드가 가까운 위치에 저장되지 않을 수 있음.
- 트리의 높이: 이진 트리는 팬아웃이 2이기 때문에 높이는 전체 노드 수의 로그 값. 따라서 특정 노드를 찾기 위해 O(logN)번의 탐색과 디스크 전송이 필요. 팬아웃이 낮은 트리는 인메모리 자료 구조로는 유용하지만 노드의 크기가 작은 탓에 외부 스토리지 저장에는 비효율적임.

디스크 저장에 적합한 트리의 특성  
- 인접한 키의 지역성을 높이기 위한 높은 팬아웃
- 트리 순회 중 디스크 탐색 횟수를 줄이기 위한 낮은 트리 높이

## 디스크 기반 자료 구조
메모리에 데이터 전부를 저장할 수 없을 때 주로 사용. 데이터 일부를 메모리에 캐시하고 나머지는 효율적으로 접근할 수 있는 형태로 디스크에 저장.  
저장 매체의 구조를 고려해서 설계해야 하며 디스크 접근 횟수를 최소화해야 함. 내부 구조를 최적화하고 지역성을 높여 페이지를 넘나드는 포인터를 최소화해야 함.

## 유비쿼터스 B-트리
B-트리는 검색 항목을 빠르게 찾을 수 있는 계층형 자료 구조. 팬아웃이 높고 높이가 낮은 이진 탐색 트리 기반 트리. 키의 순서가 보장되는 자료 구조. 노드 키를 기준으로 정렬해서 저장하기 때문에 이진 탐색과 같은 알고리즘을 사용해 특정 키를 찾을 수 있음. 시간 복잡도는 로그 시간.  
B-트리를 사용해 포인트 쿼리와 범위 쿼리를 효율적으로 수행할 수 있음. 대부분의 쿼리 언어에서 동등 조건식을 사용하는 포인트 쿼리는 개별 원소를 검색할 때, 비교 조건식을 사용하는 범위 쿼리는 여러 원소를 검색할 때 사용.  

## B-트리 계층
B-트리는 여러 노드로 구성되고 각 노드는 최대 N개의 키와 N+1개의 자식 노드 포인터를 저장.  
- 루트 노드: 트리의 최상위 노드로 부모 노드가 없음.
- 내부 노드: 루트와 리프 노드를 연결하는 모든 노드. 트리에는 일반적으로 한 레벨 이상의 내부 노드가 있음.
- 리프 노드: 자식 노드가 없는 트리의 최하위 계층 노드.

보유 가능한 노드 용량과 실제로 보유하고 있는 키의 개수의 비율 -> 점유율.  
각 노드에 저장할 수 있는 최대 키 수를 의미하는 팬아웃은 중요한 속성임. 팬아웃이 높으면 트리의 균형을 유지하는 데 필요한 트리 구조 변경 비용을 낮출 수 있고 키와 포인터를 같은 블록 또는 연속된 블록에 저장해 불필요한 탐색을 줄일 수 있음. 밸런싱 작업은 노드에 빈 공간이 없거나 거의 비었을 때 수행.

## 구분 키
각 키는 트리를 해당 키 범위의 서브트리로 분할. 정렬돼 있기 때문에 이진 검색에 사용 가능.  
각 구분 키는 서브트리에 속한 키 값들의 경계값으로 생각하면 됨.  
일부 변형 B-트리에서는 효율적인 범위 스캔을 위해 리프 노드에 형제 노드를 가리키는 포인터를 저장하여 부모를 거치지 않고 형제 노드에 바로 접근할 수 있도록 함.  
이진 트리와 반대로 상향식으로 트리를 구성하고 리프 노드가 많아질수록 내부 노드와 높이가 증가. 나중에 삽입 및 업데이트될 노드의 공간을 미리 확보해두며 공간 활용률은 최대 50%까지 낮아질 수 있지만 일반적으로 이보다 높음. 높은 점유율은 성능에 부정적인 영향 미치지 않음.

## B-트리 탐색의 시간 복잡도
특정 키를 찾기 위해서 최대 log(k)M개의 페이지에 접근해야 함. 루트에서 리프까지 거쳐 가는 자식 포인터의 수는 트리의 최대 레벨 또는 높이와 같음.  
비교 횟수 관점에서는 각 노드 안에서 이진 탐색을 사용해 키를 찾기 때문에 복잡도는 log(2)M이다.  
일반적으로 B-트리의 탐색 시간 복잡도는 logM.

## B-트리 탐색 알고리즘
루트 노드에서부터 이진 검색 수행. 검색 키보다 큰 첫 번째 구분 키를 찾고 인접한 두 개의 키 사이의 범위를 포함하는 서브트리를 찾아 리프 노드까지 포인터를 따라감. 이 과정을 반복하면서 대상 키를 찾아 반환하거나 트리에 존재하지 않는 키인 경우 바로 앞의 값을 반환.

## 키 개수
페이지에 k~2k개의 키가 있으며 최소 k+1에서 최대 2k+1개 자식 노드를 가리키는 포인터를 저장할 수 있음. 루트 페이지는 1~2k개의 키를 포함할 수 있으며 리프가 아닌 모든 페이지는 최대 l+1개의 키를 포함.  

## B-트리 노드 분할
남은 공간이 없는 리프 노드를 오버플로우 상태라고 표현. 오버플로우 상태의 노드에 새로운 키를 삽입하려면 노드를 분할해야 함.  
- 리프 노드: 노드에 최대 N개의 키-값 쌍을 저장할 수 있고 새로운 키-값 쌍 삽입 시 용량이 초과되는 경우 
- 리프가 아닌 노드: 노드에 최대 N+1개의 포인터를 저장할 수 있고 포인터 추가 시 용량이 초과되는 경우  
노드 분할은 새로운 노드를 할당해 키의 절반을 새로운 노드로 옮기고 첫번째 키와 포인터를 부모 노드에 추가하는 방식으로 이루어 짐. 이러한 키를 승급했다고 표현. 분할이 발생한 키는 분할 지점. 부모 노드에 승급 키와 포인터를 추가할 공간이 없을 경우, 부모 노드의 분할이 재귀적으로 전파될 수 있음.  
트리에 용량이 부족할 경우에는 루트 노드를 분할. 기존 루트 노드와 생성된 형제 노드는 새로 생성된 루트 노드의 다음 레벨로 강등됨. 트리 높이 증가. 리프와 내부 노드 레벨에서의 분할은 트리의 높이에 영향 X.  

요약.  
1. 새로운 노드 할당.
2. 분할 노드 키의 절반을 새로운 노드로 복사.
3. 새로운 키를 알맞은 노드에 삽입.
4. 분할 노드의 부모 노드에 분할 키와 새로운 노드를 가리키는 포인터를 추가.

## B-트리 노드 병합
키를 삭제하다 보면 노드에 저장된 값이 너무 적은 경우, 형제 노드들을 병합해야 함. -> 언더플로우.  
- 리프 노드: 노드에 최대 N개의 키-값 쌍을 저장할 수 있고 두 노드의 총 키-값 쌍의 수가 N보다 작거나 같은 경우
- 리프가 아닌 노드: 노드에 최대 N+1개의 포인터를 저장할 수 있고 두 노드의 포인터 수의 합이 N+1보다 작거나 같은 경우  
비 리프 노드를 병합하면 부모 노드에서 해당 구분 키를 가져오게 됨. 분할과 마찬가지로 병합도 루트 노드까지 재귀적으로 전파될 수 있음.

요약.
1. 모든 키를 오른쪽 노드에서 왼쪽 노드로 복사.
2. 부모 노드에서 오른쪽 노드를 가리키는 포인터를 제거(리프 노드 병합이 아니면 강등).
3. 오른쪽 노드 제거.

# 3장. 파일 포맷

## 바이너리 인코딩

### 기본형
키와 값은 integer, date, string 등의 지정된 자료형이 있고 바이너리 형식으로 표현할 수 있음.  
대부분의 숫자형은 고정 길이 자료형. 멀티바이트 숫자형을 사용할 때 인코딩과 디코딩은 모두 같은 바이트 순서를 사용해야 함. 여기서 엔디언은 바이트 배열 순서를 정의함.  

- 빅 엔디언: 최상위 바이트부터 시작해서 내림차순으로 저장. 즉, MSB를 가장 낮은 주소에 저장.
- 리틀 엔디언: 최하위 바이트부터 높은 자리 바이트까지 오름차순으로 저장.  

레코드는 숫자, 문자열, 불리언과 같은 기본형과 이들의 조합으로 구성됨. 레코드는 바이트 시퀀스 형태로 네트워크를 통해 전송되고 디스크에 저장함. 따라서 전송 및 쓰기 전에 우선 직렬화하고 수신 및 읽기 전에 역직렬화 해야 함.  

## 문자열과 가변 길이 데이터
문자열과 가변길이 자료형은 배열의 크기 또는 문자열의 길이를 나타내는 숫자와 size 바이트 크기의 실제 데이터로 구성.

## 비트 묶음형 데이터: 불리언, 열거형, 플래그
불리언 자료형은 단일 바이트 또는 true와 false를 1과 0으로 인코딩한 값을 표현. 8개의 불리언 값이 각 1비트 씩 사용하도록 묶어 쓰기도 함.  
Enum은 열거형의 줄임말이며 숫자를 표현. 바이너리 포맷과 통신 프로토콜에서 주로 사용.  
플래그는 묶음형 불리언과 열거형의 조합. 상호배타적이지 않은 불리언 값들을 표현 가능.

## 파일 포맷 설계 원칙
일반적으로 파일 포맷을 설계할 때 주소 지정 방식부터 결정해야 함. 파일을 단일 블록 또는 연속된 여러 블록으로 구성된 같은 사이즈의 페이지로 나눌 것인지 선택해야 함.  
일반적으로 파일은 고정 크기의 헤더로 시작하며 끝부분에 고정 크기의 트레일러가 있을 수도 있음. 여기에 빠르게 접근해야 하거나 파일의 나머지 부분을 디코딩하는 데 필요한 보조 정보가 들어감.  
대부분의 데이터 스토어에는 테이블의 필드 수와 순서, 형식이 고정된 스키마가 존재.  
더 복잡한 파일 구조에는 더 많은 계층이 필요.  
데이터베이스 파일은 일반적으로 여러 부분으로 구성되고 탐색에 유용한 룩업 테이블을 유지하고 각 레코드의 시작점을 가리키는 오프셋은 헤더와 트레일러 또는 개별 파일에 저장.

## 페이지 구조
구조적 관점에서 B-트리 노드는 키와 데이터 레코드 쌍을 저장하는 리프 노드 그리고 키와 다른 노드를 가리키는 포인터를 저장하는 비 리프 노드로 나뉨. B-트리 노드는 단일 페이지 또는 연결된 여러 페이지로 구성.

단점  
- 오른쪽 빈 공간이 아닌 곳에 키 추가 시 여러 원소를 재배치해야 함.
- 고정 길이 레코드 저장에 적합하지만 가변 길이 레코드를 효율적으로 관리 및 저장할 수 없음.

## 슬롯 페이지
가변 길이 레코드 저장 시 발생하는 가장 큰 문제는 삭제된 레코드의 공간 회수 시의 공간 관리.  
페이지를 여러 개의 고정 길이 세그먼트로 분할하면 가변 길이 레코드를 저장할 수 있지만 여전히 공간 낭비는 피할 수 없음.  

페이지 포맷의 조건
- 최소한의 오버헤드로 가변 길이 레코드 저장
- 삭제된 레코드의 메모리 회수
- 페이지의 레코드를 정확한 위치와 상관없이 참조

슬롯 페이지에는 페이지와 셀에 대한 중요한 정보를 저장하는 고정 길이의 헤더가 있음. 셀에는 키와 포인터, 레코드 등 임의의 데이터를 저장할 수 있으며 셀마다 크기는 다를 수 있음. 

슬롯 페이지는 위의 조건을 모두 충족함.
- 오버헤드 최소화: 실제 레코드 위치를 가리키는 포인터 배열 사용이 유일한 오버헤드
- 공간 회수: 단편화 제거 및 페이지 재구성을 통해 공간을 회수 가능
- 동적 레이아웃: 슬롯은 ID를 통해 페이지 외부에서 접근하기 때문에 정확한 위치는 페이지 내부에서만 필요

## 셀 구조
플래그와 열거형, 기본형을 사용해 셀 레이아웃을 설계할 수 있음. 셀을 병합하면 페이지가 되고 페이지를 병합하면 트리가 됨. 셀은 키 셀과 키-값 셀로 나눌 수 있음.  
같은 페이지의 셀은 모두 형식이 같다고 가정.  

키 셀의 구성 요소  
- 셀 종류
- 키 길이
- 셀이 가리키는 자식 페이지의 ID
- 키 바이트 수

키-값 셀의 구성요소  
- 셀 종류
- 키 길이
- 값 길이
- 키 바이트
- 데이터 레코드 바이트

오프셋과 페이지 ID는 정확히 구분해야 함. 고정 크기의 페이지는 페이지 캐시가 관리하기 때문에 페이지 ID를 통해 룩업 테이블에서 오프셋을 참조할 수 있음. 반면 셀 오프셋은 페이지 내부에서 시작 오프셋으로부터 상대적인 위치를 나타내기 때문에 비교적 작은 숫자를 사용해 위치를 나타낼 수 있음.

## 셀 병합으로 슬롯 페이지 구성
키는 삽입 순서대로 추가하고 셀 오프셋 포인터는 키 (논리적)순서대로 저장. 이렇게 하면 셀을 삽입 또는 업데이트, 삭제해도 다른 셀을 제배치 하지 않아도 됨.

## 가변 길이 데이터 관리
페이지 레코드 삭제 시 실제로 셀을 지우고 할당 해제된 공간으로 다른 셀을 옮길 필요는 없음. 삭제된 셀이라고 표시하고 메모리에 저장된 사용가능 목록에 회수된 메모리 크기와 해당 위치를 가리키는 포인터를 업데이트 해도 됨. 새로운 셀을 삽입하기 전에 먼저 이 목록에 적합한 세그먼트가 있는지 확인.  
세그먼트는 두 가지 전략에 따라 선택할 수 있음.
- 최초 적합: 첫 번째로 찾은 적합한 세그먼트를 선택한다. 하지만 남은 공간이 또 다른 셀을 저장해 크기가 작을 수 있기 때문에 오버헤드가 발생할 수 있다.
- 최적 적합: 레코드를 저장할 수 있는 가장 작은 세그먼트를 선택.

## 버전 관리
데이터베이스 시스템 개발사는 신규 기능 추가와 버그 수정, 성능 개선 등을 포함하는 업데이트를 지속적으로 제공하는데 이 과정에서 바이너리 파일의 구조가 변경 될 수 있음. 그래서 일반적으로 스토리지 엔진은 한  개 이상의 직렬화 포맷을 지원.  

## 체크섬
디스크에 저장된 파일은 소프트웨어 버그와 하드웨어 장애 등으로 인해 손상될 수 있음. 이런 상황을 사전에 파악하고 손상된 데이터가 다른 서브시스템에 전파되는 것을 방지하기 위해 체크섬과 CRC를 사용.  
데이터를 디스크에 쓰기 전에 체크섬을 미리 계산하고 데이터와 함께 저장. 데이터 요청 시 체크섬을 다시 계산하고 저장된 체크섬과 비교. 값이 일치하지 않는다면 데이터는 손상된 것임.  
파일 전체 에대한 체크섬을 계산하는 것은 비효율적이기 때문에 일반적으로 페이지 단위로 체크섬을 계산하고 페이지 헤더에 저장. -> 체크섬이 더 견고해지고 특정 페이지의 손상을 전체 페이지의 폐기로 이어지지 않게 함.

# 4장. B-트리 구현

## 페이지 헤더
일반적으로 페이지 내용을 나타내는 플래그와 레이아웃, 셀 개수, 빈 공간을 가리키는 하한 및 상한 오프셋과 같은 몇 가지 유용한 메타데이터를 저장.

## 매직 넘버
상수 값을 포함하는 멀티바이트 블록이며 페이지의 종류와 버전과 같은 정보 포함. 검증과 상태 체크에도 사용.

## 형제 링크
좌우에 있는 페이지를 가리키도록 순방향 리크와 역방향 링크를 저장하는 방식으로 트리를 구현하기도 하는데 이렇게 하면 부모 노드를 거슬러 올라가지 않고 이웃 노드를 바로 참조할 수 있다는 장점이 있음. 대신 노드 분할과 병합시 형제 노드의 링크까지 업데이트를 해야한다는 점에서 단점이 있음.

## 가장 오른쪽 포인터
대부분의 구분 키의 구조는 자식 포인터가 있고 마지막 포인터는 어떤 키와도 연관되지 않기 때문에 따로 저장함. 가장 오른쪽 자식 노드가 분할되고 부모에 새로운 셀이 추가되면 부모의 마지막 포인터도 다시 설정해야 함.

## 하이 키
각 트리 노드의 가장 오른쪽 포인터와 노드의 하이키를 함께 저장하는 방법도 있음. 하이 키는 현재 노드의 서브트리에 저장된 가장 큰 키를 나타냄. 이 키는 포인터 Pn이 가리키는 서브트리에서 가장 큰 키를 나타내므로 이 키 값이 해당 서브트리에 저장할 수 있는 최댓값이 됨.  
하이 키를 저장하는 트리는 각 노드에 저장된 키와 포인터의 개수가 같으며, 모든 셀에는 키-포인터 쌍이 존재. 이에 따라 에지 케이스가 줄어들고 가장 오른쪽 포인터의 처리가 단순해짐.

## 오버플로우 페이지
B-트리 알고리즘에서 모든 노드는 일정 개수의 키를 유지해야하는데 각 노드에 저장된 값의 크기가 다를 수 있기 때문에 노드가 가득 찬 상태가 아니지만 이 노드를 저장하는 고정 크기의 페이지에는 남은 공간이 없을 수 있음. 페이지 크기 증가 및 확장은 불가피 하지만 이는 굉장히 비효율적임.
