## 하테나 북마크의 데이터 규모
### 데이터가 많을수록 처리에 시간이 걸린다.

### 하테나 북마크를 예로 본 대규모 데이터
하테나 북마크의 어느 엔트리에 어떤 키워드가 포함되어 있는지를 나타내는 DB 테이블의 건수를 출력하면 3억 5천만 레코드가 존재함. 이 테이블에 갑자기 select * from relword와 같은 쿼리를 실행하면 응답이 반환되지 않는데, 그 이유는 3억 레코드 이상이 존재하기 때문.

### 하테나 북마크의 데이터 규모
위 경우 이외에도 레코드 건수가 1,500만이나 5,000만 정도는 됨. 데이터 크기로는 entry라는 테이블이 3GB, bookmark라는 테이블이 5.5GB, tag 테이블이 4.8GB, 그리고 HTML 텍스트 데이터도 압축해서 저장하고 있는데, 이것이 200GB를 넘음. relword라는 키워드용 테이블도 대략 10GB 정도. 전체적으로 간단히 말해 기가 바이트 단위임.  
Google이나 Yahoo!가 사용하고 있는 규모가 되면 테라바이트, 페타바이트가 되므로 이는 초대규모이며, 이에 비교하자면 하테나는 대규모~중규모 정도임.  
보통 웹 애플리케이션을 만들면서 기가바이트 단위의 DB는 좀처럼 나오지 않으므로 일반적인 웹 애플리케이션이라는 관점에서 보면 큰 규모임. 하테나 북마크는 일본에서 최대의 소셜 북마크 서비스로, 이 정도 데이터 규모의 웹 서비스로는 하테나 북마크가 사용자 수 관점에서도 큰 규모라고 할 수 있음. 

### 대규모 데이터로의 쿼리 – 데규모 데이터를 다루는 감각
레코드 수가 수천만 건 단위, 데이터 크기는 수 GB부터 수백 GB. 이 정도의 데이터가 되면 아무 생각 없이 던진 쿼리에 대해 응답하지 않음.  
데이터가 많으면 처리하는데 시간이 걸리게 됨.

## 대규모 데이터 처리의 어려운 점
### 메모리와 디스크

### 대규모 데이터는 어떤 점이 어려운가? - 메모리 내에서 계산할 수 없다.
제1포인트는 ‘메모리 내에서 계산할 수 없다’는 점. 메모리 내에서 계산할 수 없다는 점이 어려운 점인 이유는 메모리에 올리지 않으면 기본적으로 디스크를 계속 읽어가면서 검색하게 되어 좀처럼 발견할 수 없는 상태가 되기 때문. 데이터 건수가 많으면 그만큼 입력 데이터 건수가 늘어나므로 계산량이 많아진다는 점도 당연한 이유이지만, 이 점보다 문제가 되는 것은 ‘디스크를 읽고 있다’는 점.  
다시 말해 대규모 데이터의 어려운 점을 단적으로 말하면, ‘메모리 내에서 계산할 수 없다’는 것. 메모리 내에서 계산할 수 있다면, 아무리 무식한 방법으로 하더라도 그런대로 계산은 빨리 이뤄져서 200초나 기다릴 일은 없을 것임. 그러나 데이터가 너무 많으면 메모리 내에서 계산할 수 없으므로 디스크에 두고 특정 데이터를 검색하게 됨. 디스크는 메모리에 비해 상당히 느리므로 시간이 오래 걸림.

### 메모리와 디스크의 속도차 – 메모리는 10^5~10^6배 이상 고속
메모리 내의 특정 번지에 있는 데이터를 찾는 데이터 탐색과 디스크의 특정 원반 내에 있는 데이터를 찾는 것은 10^5~10^6 정도의 차이가 남. 10만~100만 배.

### 디스크는 왜 늦을까? - 메모리와 디스크
메모리는 전기적인 부품이므로 물리적 구조는 탐색속도와 그다지 관계없음.  
디스크는 동축 상에 ‘원반’(disk)이 쌓여 있음. 이 원반이 회전하고 있고 여기서 데이터를 읽어냄. 즉, 메모리와는 달리 회전 등의 물리적인 동작을 수반하고 있음. 이 물리적인 구조가 탐색속도에 영향을 줌.  
메모리는 1회 탐색할 때 마이크로초면 되지만, 디스크는 수 밀리초가 걸림.  
데이터가 메모리 상에 있다면 탐색할 때 물리적인 동작 없이 실제 데이터 탐색 시의 오버헤드가 거의 없으므로 빠른 것.  
탐색에 사용되는 것이 CPU의 캐시에 올리기 쉬운 알고리즘이나 데이터 구조라면 메모리 내용이 CPU 캐시에 올라가므로 더욱 빨리 처리할 수 있음(나노초 단위).

### OS 레벨에서의 연구
디스크는 느리지만 OS는 이것을 어느 정도 커버하는 작용을 함. OS는 연속된 데이터를 같은 위치에 쌓고 데이터를 읽을 때 1바이트씩 읽는 것이 아니라 4KB(kilobytes) 정도를 한꺼번에 읽도록 되어 있음.  
이렇게 함으로써 비슷한 데이터를 비슷한 곳에 두어 1번의 디스크 회전으로 읽는 데이터 수를 많게 하고, 그 결과 디스크의 회전 횟수를 최소화할 수 있게 됨. 그럼에도 결국 회전 1회당 밀리초 단위이므로 역시 메모리와의 속도 차를 피할 수 있는 것은 아님.

### 전송속도, 버스의 속도 차
메모리와 디스크는 모두 CPU와 버스로 연결되어 있음. 찾은 데이터를 디스크에서 메모리로 보내거나 메모리에서 CPU로 보내는 등 컴퓨터 내부에서 전송하기 위한 전송하기 위한 속도 차는 대략 100배 정도 차이남.  
메모리와 CPU는 상당히 빠른 버스로 연결되어 있음. 데이터가 많아지면 많아질수록 디스크와 메모리의 차이도 나타나게 되므로 전송속도에서도 디스크는 늦어짐.  
최근 나오고 있는 SSD(Solid State Drive)는 물리적인 회전이 아니므로 Seek(탐색)은 빠르지만 버스 속도가 병목이 되거나 그 밖의 구조에 기인하는 면이 있어서 역시 메모리만큼의 속도는 나오지 않음.

## 규모조정의 요소

### 규모조정, 확장성
대규모 환경이라고 하면 서버를 여러 대 나열해 놓고 그 서버로 부하를 분산함. 웹 서비스에서 자주 거론되는 규모조정(scaling), 확장성(scalability)이 해당 내용.  
웹 서비스에서는 고가의 빠른 하드웨어를 사서 성능을 높이는 ‘스케일업(scale-up)’ 전략보다도 저가이면서 일반적인 성능의 하드웨어를 많이 나열해서 시스템 전체 성능을 올리는 ‘스케일아웃(scale-out)’ 전략이 주류임. 스케일아웃 전략이 더 나은 이유는 웹 서비스에 적합한 형태이고 비용이 저렴하다는 점과 시스템 구성에 유연성이 있다는 점이 포인트.  
시스템 구성의 유연성이란, 예를 들어 부하가 적을 때는 최소한으로 투자하고 부하가 높아짐에 따라 확장해가기 쉽다는 것, 혹은 상당한 용도의 서버도 저렴하고 간단하게 준비할 수 있음. 여러모로 빠르게 상황대처가 쉬움.

### 규모조정의 요소 – CPU 부하와 I/O 부하
스케일아웃은 하드웨어를 나열해서 성능을 높이는, 즉, 하드웨어를 횡으로 전개해서 확장성을 확보해가게 됨. 이때 CPU 부하의 확장성을 확보하기는 쉬움.  
HTTP 요청을 받아 DB에 질의하고 DB로부터 응답받은 데이터를 가공해서 HTML로 클라이언트에 반환할 때는 기본적으로 CPU 부하만 소요되는 부분임. 이것은 서버 구성 중 프록시나 AP 서버(application server)가 담당할 일임.  
DB 서버 측면에서는 I/O 부하가 걸림.

### 웹 애플리케이션과 부하의 관계
웹 애플리케이션의 3단 구조에는 프록시, AP 서버, DB가 있음.  
기본적으로 AP 서버에는 I/O 부하가 걸리지 않고 DB 측에 I/O 부하가 걸림.  
AP 서버는 CPU 부하만 걸리므로 분산이 간단함. 그 이유는 기본적으로 데이터를 분산해서 갖고 있는 것이 아니므로 동일한 호스트가 동일하게 작업을 처리하기만 하면 분산할 수 있음. 따라서 대수를 늘리기만 하면 간단히 확장해갈 수 있음. 결국 새로운 서버를 추가하고자 한다면 원래 있던 서버와 완전히 동일한 구성을 갖는 서버, 심하게 말하면 복사본을 마련해서 추가하면 됨. 요청을 균등하게 분산하는 것은 로드밸런서(load balancer)라는 장치가 해줌.  
I/O 부하에는 문제가 있음. DB를 추가한다고 하면 예를 들어 쓰기가 발생했을 때 추가된 DB에 데이터를 어떻게 동기화할 것인가라는 문제가 생김. 쓰기는 간단히 분산할 수가 없음.

### DB 확장성 확보의 어려움
대규모 환경에서는 I/O 부하를 부담하고 있는 서버는 애초에 분산시키기 어려운데다가 디스크 I/O가 많이 발생하면 서버가 금새 느려지는 본질적인 문제가 있음.  
서비스가 무거울 때 서버를 늘려서 해결할 수 있다면 간단한 일임. 하지만 그렇게 해결되지 않기 때문에 어려운 것.

## OS의 캐시구조

### OS의 캐시 구조를 알고 애플리케이션 작성하기 – 페이지 캐시
OS에는 디스크 내의 데이터에 빠르게 액세스할 수 있도록 하는 구조가 갖춰져 있음. OS는 메모리를 이용해서 디스크 액세스를 줄임.  
Linux의 경우 페이지 캐시(page cache), 버퍼 캐시(buffer cache)라고 하는 캐시 구조를 갖추고 있음.  
OS는 ‘가상 메모리 구조’를 갖추고 있음. 가상 메모리 구조는 논리적인 선형 어드레스를 물리 어드레스로 변환하는 것.

### 가상 메모리 구조
가상 메모리 구조가 가장 큰 이유는 물리적인 하드웨어를 OS에서 추상화하기 위함.  
OS는 메모리를 직접 프로세스로 넘기는 것이 아니라 일단 커널 내에서 메모리를 추상화하고 있음. 이것이 가상 메모리 구조.  
디스크의 경우에도 OS가 모아서 읽어낸다고 했는데, 메모리를 확보할 때에도 그와 마찬가지 방식으로 메모리 1바이트씩 액세스하는 것이 아니라 적당히 4KB 정도를 블록으로 확보해서 프로세스에 넘김. 여기서 1개의 블록을 ‘페이지’라고 함. OS는 프로세스에서 메모리를 요청받으면 페이지를 1개 이상, 필요한 만큼 페이지를 확보해서 프로세스에 넘기는 작업을 수행함.

### Linux의 페이지 캐시 원리
OS는 확보한 페이지를 메모리상에 계속 확보해두는 기능을 갖고 있음.  
OS는 디스크로부터 4KB 크기의 블록을 읽어냄. 읽어낸 데이터는 한 번은 메모리상에 위치시켜야 프로세스가 액세스 할 수 있음(가상 메모리). 그리고 OS는 그 메모리 주소를 프로세스에 가상 어드레스로서 알려줌. 그러면 프로세스는 해당 메모리에 액세스하게 됨.  
데이터 읽기를 마친 프로세스는 해당 데이터가 불필요하게 됐어도 메모리에 남겨 두고 그렇게 하면 다음에 다른 프로세스가 같은 데이터를 디스크에서 읽어야할 때 남겨두었던 페이지를 사용할 수 있으므로 불필요한 디스크 읽기를 피할 수 있음. 이것이 페이지 캐시. 즉, 커널이 한 번 할당한 메모리를 해제하지 않고 계속 남겨두는 것이 페이지 캐시의 기본.  
이는 예외인 경우를 제외하고 모든 I/O에 투과적으로 작용함. Linux에서는 디스크에 데이터를 읽으러 가면 꼭 한 번은 메모리로 가서 데이터가 반드시 캐싱됨. 이로인해 두 번째 액세스가 빨라짐. 현대의 OS는 대체로 페이지 캐시와 비슷한 구조를 갖추고 있음. OS를 계속 가동 시켜 두면 메모리가 허락하는 한 디스크 상의 데이터를 계속 캐싱함. 따라서 OS를 계속 켜두면 빨라짐.  

### VFS
디스크의 캐시는 페이지 캐시에 의해 제공되지만, 실제 이 디스크를 조작하는 디바이스 드라이버와 OS 사이에는 파일 시스템이 끼어 있음. 파일 시스템 하위에는 디바이스 드라이버가 있으며, 디바이스 드라이버가 실제로 하드디스크 등을 조작. 파일시스템 위에는 VFS(Virtual File System, 가상 파일시스템)이라는 추상화 레이어가 있음. 파일시스템은 다양한 함수를 갖추고 있는데, 그 인터페이스를 통일하는 것이 VFS의 역할. 또한 VFS가 페이지 캐시의 구조를 지니고 있음.  VFS의 역할은 파일 시스템 구현의 추상화와 성능에 관련된 페이지 캐시 부분.

###Linux는 페이지 단위로 디스크를 캐싱한다
OS는 파일을 읽어낸 블록 단위만으로 캐싱할 수 있는 범위가 정해짐. 디스크상에 배치되어 있는 특정파일의 일부분만, 읽어낸 부분만 캐싱 가능. 이렇게 디스크를 캐싱하는 단위가 페이지.  구조상으로는 LRU(Least Recently Used), 가장 오래된 캐싱된 페이지를 파기하고 가장 새로운 것을 남겨놓는 형태로 되어 있으므로 최근에 읽은 부분이 캐시에 남고 과거에 읽은 부분은 파기됨. 따라서 DB도 계속 구동시키면 캐시가 점점 최적화되어 가므로 기동시킨 직후보다 점점 뒤로 갈수록 부하, I/O가 내려가는 특성을 보임.  
Linux는 파일을 i노드 번호라고 하는 번호로 식별하며, 해당 파일의 i노드 번호와 해당 파일의 어느 위치부터 시작할지를 나타내는 오프셋, 이 두 가지 값을 키로 캐싱함. 이 두 가지를 키로 하면 ‘어떤 파일의 어느 위치를’이라는 쌍으로 캐시의 키를 관리할 수 있으므로 결과적으로 파일 전체가 아닌 파일의 일부를 캐싱해갈 수 있음.  
그리고 파일이 아무리 크더라도 이 키로부터 해당 페이지를 찾을 때의 데이터 구조는 최적화되어 있음. OS(=커널) 내부에서 사용되고 있는 데이터 구조는 Radix Tree라고 하며, 파일이 아무리 커지더라도 캐시 탐색속도가 떨어지지 않도록 개발된 데이터 구조임. 따라서 커다란 파일의 일부분을 캐싱하거나 작은 파일의 일부분을 캐싱하더라도 동일한 속도로 캐시를 찾을 수 있도록 되어 있음.

### 메모리가 비어 잇으면 캐싱
Linux는 메모리가 비어 있으면 전부 캐싱함. 프로세스에서 메모리를 요청했을 때 캐시로 인해 더 이상 메모리가 남아있지 않다면 오래된 캐시를 버리고 프로세스에 메모리를 확보해줌.  

### 메모리를 늘려서 I/O부하 줄이기
메모리를 늘리면 캐시에 사용할 수 있는 용량이 늘어나고, 캐시에 사용할 수 있는 용량이 늘어나면 보다 많은 데이터를 캐싱할 수 있고, 많이 캐싱되면 디스크를 읽는 횟수가 줄어듦.  

### 페이지 캐시는 투과적으로 작용한다
특정 파일을 read하면 이를 쭉 캐싱해나감.

## I/O 부하를 줄이는 방법

### 캐시를 전제로 한 I/O 줄이는 방법
첫 번째 포인트는 데이터 규모에 비해 물리 메모리가 크면 전부 캐싱할 수 있음. 다루고자 하는 데이터의 크기에 주목.  
또한 대규모 데이터 처리에는 데이터 압축이 중요한데, 압축해서 저장해두면 디스크의 내용을 전부 그대로 캐싱해둘 수 있는 경우가 많음.  
또 하나는 경제적인 비용과의 밸런스를 고려하고자 한다는 점.

### 복수 서버로 확장시키기 – 캐시로 해결될 수 없는 규모일 경우
메모리를 늘려서 전부 캐싱할 수 있다면 좋지만, 데이터를 전부 캐싱할 수 없는 규모가 될 수 있음. 이때 복수 서버로 확장시키는 방안을 생각해볼 필요가 있음.  
AP 서버를 늘려야 하는 이유는 기본적으로 CPU 부하를 낮추고 분산시키기 위함. 하지만 DB 서버를 늘려야 할 때는 반드시 부하 때문만은 아니고 오히려 캐시 용량을 늘리고자 할 때 혹은 효율을 높이고자 할 때인 경우가 많음.  
따라서 AP 서버를 늘리는 것과 DB 서버를 늘리는 것은 둘 다 서버를 늘리는 것이지만 필요한 리소스, 요구되는 리소스가 전혀 다름.

### 단순히 대수만 늘려서는 확장성을 확보할 수 없다
서버를 늘림으로써 시스템 전체로서는 아주 조금은 빨라질지도 모르지만, 증설비용에 대비해서 성능향상은 극히 부족함.

## 국소성을 살리는 분산

### 국소성을 고려한 분산이란?
데이터에 대한 액세스 패턴을 고려해서 분산시키는 것을 국소성을 고려한 분산이라고 함.  
액세스 패턴을 고려해서 분배한 경우에는 더 이상 액세스되지 않는 캐시영역을 다른 곳으로 돌릴 수 있음. 결국 시스템 전체로서는 메모리에 올라간 데이터량이 늘어나게 됨.

### 파티셔닝 – 국소성을 고려한 분산 1
파티셔닝(partitioning)은 한 대였던 DB 서버를 여러 대의 서버로 분할하는 방법을 말함. 간단한 것은 ‘테이블 단위 분할’.  
테이블 단위로 분할했으면 요청도 각 서버로 보내 처리될 수 있도록 당연히 애플리케이션을 변경할 필요가 있음.  
다른 분할 방법으로는 ‘테이블 데이터 분할’이 있음. 특정 테이블 하나를 여러 개의 작은 테이블로 분할함.  
이 분할의 문제점은 분할의 입도를 크거나 작게 조절할 때 데이터를 한 번 병합해야 한다는 번거로움이 있다는 점.

### 요청 패턴을 ‘섬’으로 분할 – 국소성을 고려한 분산 2
‘용도별로 시스템을 섬으로 나누는 방법’도 있음.  
하테나 북마크에서는 HTTP 요청의 User-Agent나 URL 등을 보고, 통상의 사용자, 일부 API요청, Google bot이나 Yahoo! 등의 봇(bot) 등에 따라 섬으로 나누는 방법을 사용하고 있음.  
검색 봇은 그 특성상 아주 오래된 웹 페이지에도 액세스하러 옴. 사람의 경우라면 좀처럼 액세스하지 않을 페이지에도 액세스하고, 또한 광범위하게 액세스함. 그렇게 되면 캐시가 작용하기 어려움. 동일한 페이지에 잇따라 방문하는 경우에는 캐시로 성능을 끌어올리기 쉽지만, 광범위한 액세스에는 그럴 수가 없음.  
그러나 봇에 대해 그렇게 빨리 응답할 필요는 없으므로 섬으로 나눠놓음.  
한편, 봇 이외의 액세스, 즉 사용자로부터의 액세스는 최상위 페이지나 인기 엔트리 페이지 등 최신, 인기 페이지에 거의 액세스가 집중되므로 빈번하게 참조되는 부분은 캐싱하기 쉬움.  
이렇듯 캐싱하기 쉬운 요청, 캐싱하기 어려운 요청을 처리하는 섬을 나누게 되면, 전자는 국소성으로 인해 안정되고 높은 캐시 적중률을 낼 수 있게 됨. 후자의 요청이 전자의 캐시를 어지럽히므로 섬으로 나누는 경우에 비해 전체적으로는 캐시 효율이 떨어짐.

### 페이지 캐시를 고려한 운용의 기본 규칙
첫 번째 포인트는 OS 기동 직후에 서버를 투입하지 않는다는 것. 캐시가 쌓여있지 않기 때문.  
다음은 성능평가나 부하시험에 대한 것. 초깃값을 버려야 한다는 것을 기억. 성능평가나 부하시험을 할 땐 캐시가 최적화된 후에 실시할 필요가 있음.
