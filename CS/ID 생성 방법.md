## 시퀀스, 자동증가
Oracle sequence, MySQL auto increment.  
DB가 알아서 ID 값을 순서대로 생성.  
트래픽이 매우 높으면 값 생성 부하도 클 수 있음.  
반드시 순서대로 생기는 건 아님.  
 - 예, Oracle RAC에서 시퀀스 사용.
8바이트 / 4바이트

## UUID
universally unique identifier  
v4 기준 - 임의의 값을 생성(자바 v4)  
(거의) 중복될 가능성이 없음.  
36글자(32개 16진수 + 대시 4글자), 128비트  
 - 바이너리로 저장하면 16바이트  
서버에서 생성하므로 ID 생성에 따른 DB 부하 없음.

## 클러스터형(clusted) 인덱스
키 값을 기준으로 데이터를 정렬 저장  
(주로) PK가 클러스터형 인덱스임.  
랜덤하게 생성되는 UUID는 INSERT 과정에서 인덱스/데이터의 이동이 더 많이 발생.  
(최신 데이터가 더 많이 조회되는 상황에서) 데이터 캐시 효율도 떨어짐.  

## UUIDv7
앞자리(48비트)에 타임스탬프가 들어감  
시간 기준 (거의) 정렬된 순서로 생성  
클러스터형 인덱스에 적합  
여전히 36글자 (바이너리로 변환해도 16바이트)  
 - 규모가 작은 곳에서는 문제 없음.
 - 규모가 작으면 시퀀스, 자동증가 써도됨.  
규모가 크면 ID가 차지하는 데이터 공간도 커짐.

## Snowflake
64비트(8바이트) ID로 구 트위터(현 X)가 만듦.  
부호비트(1): 사용하지 않음(예약).  
타임스탬프(41): 밀리초로 시간 표현. 시작 시점부터 대략 70년 사용 가능.  
 - 부호비트까지 확장하면 139년 사용 가능  
머신ID(10): 2^10(1024개 가능) - 개별 프로세스 단위로 할당  
시퀀스(12): 2^12(4096개 가능) 카운터로 매 밀리초마다 0으로 초기화  
 - 한 머신ID 기준 초당 40만개(4,096,000) ID 생성 가능  

글로벌 서비스 아님, 트래픽도 국내 최상 아님, 프로세스 몇 개 안 됨 -> 시퀀스/자동 증가로 충분, YYYYMMDDHHMM-랜덤형식도 충분  

최신 데이터를 더 많이 읽는다면, 데이터 쓰기가 많다면 -> UUID보다는 정렬 순서로 생성되는 ID 고려(클러스터형 인덱스)

100년 기업을 꿈꾼다면 Snowflake류를 변형해서 사용

RDB가 아니라면 사용할 저장소의 특성을 고려해 ID 생성 규칙 고려 -> 예, ID를 해시해서 저장
