# 1장. 소개 및 개요

## DBMS 구조  
클라이언트 요청(쿼리) -> [트랜스포트 서브시스템] -> [쿼리 프로세서] -> [실행 엔진] -> 로컬 쿼리 -> [스토리지 엔진]  

## 스토리지 엔진
- 트랜잭션 매니저: 트랜잭션 스케줄링, 논리적 일관성 보장
- 잠금 매니저: 잠금 제어, 동시 수행 작업에 대한 물리적 데이터 무결성 침해 제어  
(위 두 가지는 동시성 제어 -> 논리적 및 물리적 데이터 무결성보장 및 동시 수행 작업의 효율적인 수행 담당.)
- 액세스 메소드: 디스크에 저장된 데이터에 대한 접근 및 저장방식 정의. 힙 파일, B-트리 or LSM 트리 등의 자료 구조 사용.
- 버퍼 매니저: 데이터 페이지를 메모리에 캐시.
- 복구 매니저: 로그 유지 관리, 장애 발생 시 시스템 복구.

## 인메모리 DBMS
메모리(RAM)에 대부분의 데이터 저장, 디스크는 복구와 로그 저장 용도.  
디스크 기반 DBMS -> 데이터를 디스크에 저장, 메모리는 캐시 또는 임시 저장 용도.

### 장점
- 메모리는 디스크보다 훨씬 더 빠르게 데이터 접근.  
- 낮은 데이터 접근 비용.  
- 세밀한 접근 단위.
- 메모리 제어가 디스크 제어보다 프로그래밍적으로 더 간단함.
### 단점
- 비쌈.
- RAM의 휘발성(데이터 손실).
- 때문에 디스크가 메모리보다 유지관리 측면에서 더 간단하고 비용이 낮음.

인메모리 DBMS의 데이터 지속성을 보장하고 손실을 방지하기 위해 데이터를 디스크에 백업함.  
인메모리 시스템에서는 백업본을 유지하는데 백업본은 디스크 기반 자료 구조에 순서대로 저장.  
수정 내용은 비동기적으로 갱신(클라이언트 요청과 독립적으로 실행), I/O 작업 최소화를 위해 배치 단위로 백업, 데이터 복구 시 백업본과 로그를 기반으로 데이터 재구성.  

디스크 기반 DBMS는 디스크 접근에 특화된 특수한 자료 구조를 사용. -> 넓고 낮은 트리.  

## 로우형 데이터 레이아웃
데이터 레코드를 로우 형식으로 저장.  
여러 필드의 값을 고유 식별 키로 구분할수 있는 레코드 형식에 적합.  
한 개의 로우씩 접근하는 경우에 적합, 공간 지역성 극대화.  
특정 사용자의 모든 정보를 읽을 때는 효율적이지만 여러 사용자의 특정 필드를 읽을 때는 비효율적.

## 칼럼형 데이터 레이아웃
특정 칼럼 데이터의 추세와 평균 등을 계산하는 집계 분석 작업에 적합.  
조인과 필터링, 다중 로우 집계 등을위해 튜플을 재구성하려면 칼럼 사이의 관계를 정의하는 메타데이터가 필요.  
따라서 각 값마다 중복 저장된 키로 인해 데이터가 증가.

같은 칼럼의 여러 값을 한 번에 읽으면 캐시 활용도와 처리 효율성이 높아짐.  
자료형별로 저장하면 압축률도 증가.

데이터를 레코드 단위로 접근하고 일반 쿼리와 범위 스캔 요청이 많으면 로우형 DBMS가 적합.  
많은 로우를 스캔하거나 일부 칼럼에 대한 집계 작업이 많다면 칼럼형 DBMS가 적합.

## 와이드 칼럼 스토어
데이터를 다차원 맵으로 표현, 여러칼럼을 칼럼 패밀리 단위로 저장. 칼럼 패밀리의 데이터는 로우 형식으로 저장.  

## 데이터 파일과 인덱스 파일
- 저장 효율성: 데이터 레코드의 저장 오버헤드를 최소화하는 방식으로 파일을 구성할 수 있음.
- 접근 효율성: 최소한의 단계로 원하는 레코드를 찾을 수 있음.
- 갱신 효율성: 디스크 쓰기를 최소화하는 방식으로 레코드를 갱신.
데이터베이스 시스템은 데이터 파일과 인덱스 파일을 분리.
데이터 파일에는 데이터 레코드를 저장, 인덱스 파일에는 레코드에 대한 메타데이터를 저장하고 이를 사용해 데이터 파일에서의 레코드 위치를 찾을 수 있음.
새로운 레코드와 업데이트된 레코드는 키-값 쌍의 형식으로 저장함. 대부분의 최신 데이터베이스 시스템은 데이터를 즉시 페이지에서 삭제하지 않고 키와 타임스탬프 등의 삭제 관련 메타데이터를 저장한 삭제 마커를 사용하여 수정되거나 삭제 마커로 가려진 레코드는 가비지 컬렉션 중에 최신 레코드로 갱신되며 기존값은 삭제.

### 데이터 파일
인덱스 구조형 테이블, 힙 구조형 테이블 또는 해시 구조형 테이블을 기반으로 함.  
힙 파일은 레코드를 특정 순서를 따르지 않고 대체로 삽입 순서대로 저장함. 그러므로 새로운 페이지가 추가돼도 파일을 재구성하지 않아도 됨. 대신 데이터 검색 시 데이터의 실제 위치를 가리키는 인덱스 필요.  
해시 파일은 레코드를 각 키의 해시 값에 해당하는 버킷에 저장. 버킷 내 레코드는 삽입 순서대로 저장하거나 키 순서로 정렬하면 조회 속도를 향상 시킬 수 있음.
인덱스 구조형 테이블은 인덱스에 실제 데이터 레코드를 저장. 데이터는 키 순서로 정렬되기 때문에 IOT의 범위 스캔은 실제 값을 순서대로 읽으면서 비교. 인덱스에 데이터 레코드를 저장하면 디스크 탐색 횟수를 최소 1회로 줄일 수 있음.  
실제 데이터 레코드가 다른 파일에 저장돼 있으면 인덱스 파일에 레코드 식별자와 레코드의 위치를 저장해야 함.(데이터 파일에서 데이터의 위치를 나타내는 오프셋을 저장하거나 해시 파일의 경우 버킷 ID를 저장.)

### 인덱스 파일
디스크에 저장된 데이터 레코드를 효율적으로 검색할 수 있는 자료 구조.  
프라이머리 파일에 대한 인덱스 -> 기본 인덱스. 일반적으로 기본 인덱스는 기본 키 또는 기본 키 역할을 할 수 있는 여러 키의 조합에 대한 인덱스. 다른 인덱스는 보조 인덱스.  
보조 인덱스는 데이터 레코드를 직접 가리키거나 해당 레코드의 기본 키를 저장. 여러 보조 인덱스가 같은 레코드를 가리킬 수 있고, 하나의 레코드는 여러 다른 필드로 식별될 수 있으며 다양한 인덱스를 사용해 검색할 수 있음. 기본 인덱스는 키별로 하나의 레코드만 가리키는 반면, 보조 인덱스는 키별로 여러 레코드를 가리킬 수 있음.  
실제 데이터 레코드 정렬 순서와 검색 키의 정렬 순서가 같은 인데스를 클러스터 형 인덱스. 반대는 비클러스터형 인덱스. 기본 인덱스는 대부분 클러스터형 인덱스, 보조 인덱스는 비클러스터형 인덱스.  
대부분의 데이터베이스 시스템은 데이터 레코드를 식별할 수 있는 칼럼의 집합을 내부 키로 사용. 기본 키를 설정하지 않은 경우 내부적으로 기본 키를 자동으로 생성.

## 기본 인덱스를 통한 간접 참조
데이터를 직접 참조하면 디스크 탐색 오버헤드가 줄어듦. 대신 레코드를 갱신하거나 위치를 변경할 때마다 포인터를 수정해야 하는 오버헤드가 있음. 기본 인덱스를 통해 간접 참조하면 포인터 갱신 비용이 줄어들지만 레코드 위치를 찾는 과정 추가.  

## 버퍼링과 불변성, 순서화
- 버퍼링  
  데이터를 디스크에 쓰기 전에 일부를 메모리에 저장하는 것을 의미. 모든 디스크 기반 자료 구조에서는 버퍼를 어느 정도 사용.
- 가변성  
  파일 일부를 읽고 갱신한 뒤에 똑같은 자리에 다시 쓸지에 대한 여부를 나타내는 속성. 불변 구조에서는 한 번 쓴 파일 내용은 고칠 수 없고 파일 끝에 내용을 추가하는 추가 전용 구조.
- 순서화  
  디스크 페이지에 데이터 레코드를 키 순서로 저장하는 것을 의미. 정렬 순서상 인접한 키는 디스크의 연속된 세그먼트에 저장. 순서화는 특정 데이터 레코드 검색뿐만 아니라 효율적인 범위 스캔에 매우 중요한 속성. 반면 데이터를 임의의 순서로 저장하면 쓰기 시간 최적화.

# 2장. B-트리 개요

## 이진 탐색 트리
정렬된 인메모리 자료 구조, 키와 두 개의 자식 포인터가 저장된 여러 노드로 구성됨.  
각 노드의 키는 왼쪽 서브트리의 모든 노드 키보다 크고 오른쪽 서브트리의 모든 키보다 작음.  

## 트리 밸런싱
균형 트리란 노드 개수가 N일 때 높이가 logN이고 두 서브트리의 높이 차이가 최대 1인 트리.  
균형 트리 탐색 시간 복잡도 -> O(logN). 불균형 트리 탐색 시간 복잡도 -> O(N).  
새로운 노드 추가 시 트리의 균형을 유지해야 함. -> 노드 삽입으로 인해 트리의 균형이 깨진다면 가운데 노드를 중심으로 회전함.  

## 디스크 기반 스토리지용 트리
트리의 팬아웃(노드가 가질 수 있는 최대 자식 노드 개수)이 낮기 때문에 트리 밸런싱과 노드 재배치, 포인터 갱신이 자주 발생. 따라서 BST는 높은 트리 유지 비용 때문에 디스크 기반 자료 구조로는 적합하지 않음.  
BST를 디스크에서 제어하면 발생하는 문제.  
- 지역성: 새로운 노드와 부모 노드가 가까운 위치에 저장되지 않을 수 있음.
- 트리의 높이: 이진 트리는 팬아웃이 2이기 때문에 높이는 전체 노드 수의 로그 값. 따라서 특정 노드를 찾기 위해 O(logN)번의 탐색과 디스크 전송이 필요. 팬아웃이 낮은 트리는 인메모리 자료 구조로는 유용하지만 노드의 크기가 작은 탓에 외부 스토리지 저장에는 비효율적임.

디스크 저장에 적합한 트리의 특성  
- 인접한 키의 지역성을 높이기 위한 높은 팬아웃
- 트리 순회 중 디스크 탐색 횟수를 줄이기 위한 낮은 트리 높이

## 디스크 기반 자료 구조
메모리에 데이터 전부를 저장할 수 없을 때 주로 사용. 데이터 일부를 메모리에 캐시하고 나머지는 효율적으로 접근할 수 있는 형태로 디스크에 저장.  
저장 매체의 구조를 고려해서 설계해야 하며 디스크 접근 횟수를 최소화해야 함. 내부 구조를 최적화하고 지역성을 높여 페이지를 넘나드는 포인터를 최소화해야 함.

## 유비쿼터스 B-트리
B-트리는 검색 항목을 빠르게 찾을 수 있는 계층형 자료 구조. 팬아웃이 높고 높이가 낮은 이진 탐색 트리 기반 트리. 키의 순서가 보장되는 자료 구조. 노드 키를 기준으로 정렬해서 저장하기 때문에 이진 탐색과 같은 알고리즘을 사용해 특정 키를 찾을 수 있음. 시간 복잡도는 로그 시간.  
B-트리를 사용해 포인트 쿼리와 범위 쿼리를 효율적으로 수행할 수 있음. 대부분의 쿼리 언어에서 동등 조건식을 사용하는 포인트 쿼리는 개별 원소를 검색할 때, 비교 조건식을 사용하는 범위 쿼리는 여러 원소를 검색할 때 사용.  

## B-트리 계층
B-트리는 여러 노드로 구성되고 각 노드는 최대 N개의 키와 N+1개의 자식 노드 포인터를 저장.  
- 루트 노드: 트리의 최상위 노드로 부모 노드가 없음.
- 내부 노드: 루트와 리프 노드를 연결하는 모든 노드. 트리에는 일반적으로 한 레벨 이상의 내부 노드가 있음.
- 리프 노드: 자식 노드가 없는 트리의 최하위 계층 노드.

보유 가능한 노드 용량과 실제로 보유하고 있는 키의 개수의 비율 -> 점유율.  
각 노드에 저장할 수 있는 최대 키 수를 의미하는 팬아웃은 중요한 속성임. 팬아웃이 높으면 트리의 균형을 유지하는 데 필요한 트리 구조 변경 비용을 낮출 수 있고 키와 포인터를 같은 블록 또는 연속된 블록에 저장해 불필요한 탐색을 줄일 수 있음. 밸런싱 작업은 노드에 빈 공간이 없거나 거의 비었을 때 수행.

## 구분 키
각 키는 트리를 해당 키 범위의 서브트리로 분할. 정렬돼 있기 때문에 이진 검색에 사용 가능.  
각 구분 키는 서브트리에 속한 키 값들의 경계값으로 생각하면 됨.  
일부 변형 B-트리에서는 효율적인 범위 스캔을 위해 리프 노드에 형제 노드를 가리키는 포인터를 저장하여 부모를 거치지 않고 형제 노드에 바로 접근할 수 있도록 함.  
이진 트리와 반대로 상향식으로 트리를 구성하고 리프 노드가 많아질수록 내부 노드와 높이가 증가. 나중에 삽입 및 업데이트될 노드의 공간을 미리 확보해두며 공간 활용률은 최대 50%까지 낮아질 수 있지만 일반적으로 이보다 높음. 높은 점유율은 성능에 부정적인 영향 미치지 않음.

## B-트리 탐색의 시간 복잡도
특정 키를 찾기 위해서 최대 log(k)M개의 페이지에 접근해야 함. 루트에서 리프까지 거쳐 가는 자식 포인터의 수는 트리의 최대 레벨 또는 높이와 같음.  
비교 횟수 관점에서는 각 노드 안에서 이진 탐색을 사용해 키를 찾기 때문에 복잡도는 log(2)M이다.  
일반적으로 B-트리의 탐색 시간 복잡도는 logM.

## B-트리 탐색 알고리즘
루트 노드에서부터 이진 검색 수행. 검색 키보다 큰 첫 번째 구분 키를 찾고 인접한 두 개의 키 사이의 범위를 포함하는 서브트리를 찾아 리프 노드까지 포인터를 따라감. 이 과정을 반복하면서 대상 키를 찾아 반환하거나 트리에 존재하지 않는 키인 경우 바로 앞의 값을 반환.

## 키 개수
페이지에 k~2k개의 키가 있으며 최소 k+1에서 최대 2k+1개 자식 노드를 가리키는 포인터를 저장할 수 있음. 루트 페이지는 1~2k개의 키를 포함할 수 있으며 리프가 아닌 모든 페이지는 최대 l+1개의 키를 포함.  

## B-트리 노드 분할
남은 공간이 없는 리프 노드를 오버플로우 상태라고 표현. 오버플로우 상태의 노드에 새로운 키를 삽입하려면 노드를 분할해야 함.  
- 리프 노드: 노드에 최대 N개의 키-값 쌍을 저장할 수 있고 새로운 키-값 쌍 삽입 시 용량이 초과되는 경우 
- 리프가 아닌 노드: 노드에 최대 N+1개의 포인터를 저장할 수 있고 포인터 추가 시 용량이 초과되는 경우  
노드 분할은 새로운 노드를 할당해 키의 절반을 새로운 노드로 옮기고 첫번째 키와 포인터를 부모 노드에 추가하는 방식으로 이루어 짐. 이러한 키를 승급했다고 표현. 분할이 발생한 키는 분할 지점. 부모 노드에 승급 키와 포인터를 추가할 공간이 없을 경우, 부모 노드의 분할이 재귀적으로 전파될 수 있음.  
트리에 용량이 부족할 경우에는 루트 노드를 분할. 기존 루트 노드와 생성된 형제 노드는 새로 생성된 루트 노드의 다음 레벨로 강등됨. 트리 높이 증가. 리프와 내부 노드 레벨에서의 분할은 트리의 높이에 영향 X.  

요약.  
1. 새로운 노드 할당.
2. 분할 노드 키의 절반을 새로운 노드로 복사.
3. 새로운 키를 알맞은 노드에 삽입.
4. 분할 노드의 부모 노드에 분할 키와 새로운 노드를 가리키는 포인터를 추가.

## B-트리 노드 병합
키를 삭제하다 보면 노드에 저장된 값이 너무 적은 경우, 형제 노드들을 병합해야 함. -> 언더플로우.  
- 리프 노드: 노드에 최대 N개의 키-값 쌍을 저장할 수 있고 두 노드의 총 키-값 쌍의 수가 N보다 작거나 같은 경우
- 리프가 아닌 노드: 노드에 최대 N+1개의 포인터를 저장할 수 있고 두 노드의 포인터 수의 합이 N+1보다 작거나 같은 경우  
비 리프 노드를 병합하면 부모 노드에서 해당 구분 키를 가져오게 됨. 분할과 마찬가지로 병합도 루트 노드까지 재귀적으로 전파될 수 있음.

요약.
1. 모든 키를 오른쪽 노드에서 왼쪽 노드로 복사.
2. 부모 노드에서 오른쪽 노드를 가리키는 포인터를 제거(리프 노드 병합이 아니면 강등).
3. 오른쪽 노드 제거.

# 3장. 파일 포맷

## 바이너리 인코딩

### 기본형
키와 값은 integer, date, string 등의 지정된 자료형이 있고 바이너리 형식으로 표현할 수 있음.  
대부분의 숫자형은 고정 길이 자료형. 멀티바이트 숫자형을 사용할 때 인코딩과 디코딩은 모두 같은 바이트 순서를 사용해야 함. 여기서 엔디언은 바이트 배열 순서를 정의함.  

- 빅 엔디언: 최상위 바이트부터 시작해서 내림차순으로 저장. 즉, MSB를 가장 낮은 주소에 저장.
- 리틀 엔디언: 최하위 바이트부터 높은 자리 바이트까지 오름차순으로 저장.  

레코드는 숫자, 문자열, 불리언과 같은 기본형과 이들의 조합으로 구성됨. 레코드는 바이트 시퀀스 형태로 네트워크를 통해 전송되고 디스크에 저장함. 따라서 전송 및 쓰기 전에 우선 직렬화하고 수신 및 읽기 전에 역직렬화 해야 함.  

## 문자열과 가변 길이 데이터
문자열과 가변길이 자료형은 배열의 크기 또는 문자열의 길이를 나타내는 숫자와 size 바이트 크기의 실제 데이터로 구성.

## 비트 묶음형 데이터: 불리언, 열거형, 플래그
불리언 자료형은 단일 바이트 또는 true와 false를 1과 0으로 인코딩한 값을 표현. 8개의 불리언 값이 각 1비트 씩 사용하도록 묶어 쓰기도 함.  
Enum은 열거형의 줄임말이며 숫자를 표현. 바이너리 포맷과 통신 프로토콜에서 주로 사용.  
플래그는 묶음형 불리언과 열거형의 조합. 상호배타적이지 않은 불리언 값들을 표현 가능.

## 파일 포맷 설계 원칙
일반적으로 파일 포맷을 설계할 때 주소 지정 방식부터 결정해야 함. 파일을 단일 블록 또는 연속된 여러 블록으로 구성된 같은 사이즈의 페이지로 나눌 것인지 선택해야 함.  
일반적으로 파일은 고정 크기의 헤더로 시작하며 끝부분에 고정 크기의 트레일러가 있을 수도 있음. 여기에 빠르게 접근해야 하거나 파일의 나머지 부분을 디코딩하는 데 필요한 보조 정보가 들어감.  
대부분의 데이터 스토어에는 테이블의 필드 수와 순서, 형식이 고정된 스키마가 존재.  
더 복잡한 파일 구조에는 더 많은 계층이 필요.  
데이터베이스 파일은 일반적으로 여러 부분으로 구성되고 탐색에 유용한 룩업 테이블을 유지하고 각 레코드의 시작점을 가리키는 오프셋은 헤더와 트레일러 또는 개별 파일에 저장.

## 페이지 구조
구조적 관점에서 B-트리 노드는 키와 데이터 레코드 쌍을 저장하는 리프 노드 그리고 키와 다른 노드를 가리키는 포인터를 저장하는 비 리프 노드로 나뉨. B-트리 노드는 단일 페이지 또는 연결된 여러 페이지로 구성.

단점  
- 오른쪽 빈 공간이 아닌 곳에 키 추가 시 여러 원소를 재배치해야 함.
- 고정 길이 레코드 저장에 적합하지만 가변 길이 레코드를 효율적으로 관리 및 저장할 수 없음.

## 슬롯 페이지
가변 길이 레코드 저장 시 발생하는 가장 큰 문제는 삭제된 레코드의 공간 회수 시의 공간 관리.  
페이지를 여러 개의 고정 길이 세그먼트로 분할하면 가변 길이 레코드를 저장할 수 있지만 여전히 공간 낭비는 피할 수 없음.  

페이지 포맷의 조건
- 최소한의 오버헤드로 가변 길이 레코드 저장
- 삭제된 레코드의 메모리 회수
- 페이지의 레코드를 정확한 위치와 상관없이 참조

슬롯 페이지에는 페이지와 셀에 대한 중요한 정보를 저장하는 고정 길이의 헤더가 있음. 셀에는 키와 포인터, 레코드 등 임의의 데이터를 저장할 수 있으며 셀마다 크기는 다를 수 있음. 

슬롯 페이지는 위의 조건을 모두 충족함.
- 오버헤드 최소화: 실제 레코드 위치를 가리키는 포인터 배열 사용이 유일한 오버헤드
- 공간 회수: 단편화 제거 및 페이지 재구성을 통해 공간을 회수 가능
- 동적 레이아웃: 슬롯은 ID를 통해 페이지 외부에서 접근하기 때문에 정확한 위치는 페이지 내부에서만 필요

## 셀 구조
플래그와 열거형, 기본형을 사용해 셀 레이아웃을 설계할 수 있음. 셀을 병합하면 페이지가 되고 페이지를 병합하면 트리가 됨. 셀은 키 셀과 키-값 셀로 나눌 수 있음.  
같은 페이지의 셀은 모두 형식이 같다고 가정.  

키 셀의 구성 요소  
- 셀 종류
- 키 길이
- 셀이 가리키는 자식 페이지의 ID
- 키 바이트 수

키-값 셀의 구성요소  
- 셀 종류
- 키 길이
- 값 길이
- 키 바이트
- 데이터 레코드 바이트

오프셋과 페이지 ID는 정확히 구분해야 함. 고정 크기의 페이지는 페이지 캐시가 관리하기 때문에 페이지 ID를 통해 룩업 테이블에서 오프셋을 참조할 수 있음. 반면 셀 오프셋은 페이지 내부에서 시작 오프셋으로부터 상대적인 위치를 나타내기 때문에 비교적 작은 숫자를 사용해 위치를 나타낼 수 있음.

## 셀 병합으로 슬롯 페이지 구성
키는 삽입 순서대로 추가하고 셀 오프셋 포인터는 키 (논리적)순서대로 저장. 이렇게 하면 셀을 삽입 또는 업데이트, 삭제해도 다른 셀을 제배치 하지 않아도 됨.

## 가변 길이 데이터 관리
페이지 레코드 삭제 시 실제로 셀을 지우고 할당 해제된 공간으로 다른 셀을 옮길 필요는 없음. 삭제된 셀이라고 표시하고 메모리에 저장된 사용가능 목록에 회수된 메모리 크기와 해당 위치를 가리키는 포인터를 업데이트 해도 됨. 새로운 셀을 삽입하기 전에 먼저 이 목록에 적합한 세그먼트가 있는지 확인.  
세그먼트는 두 가지 전략에 따라 선택할 수 있음.
- 최초 적합: 첫 번째로 찾은 적합한 세그먼트를 선택한다. 하지만 남은 공간이 또 다른 셀을 저장해 크기가 작을 수 있기 때문에 오버헤드가 발생할 수 있다.
- 최적 적합: 레코드를 저장할 수 있는 가장 작은 세그먼트를 선택.

## 버전 관리
데이터베이스 시스템 개발사는 신규 기능 추가와 버그 수정, 성능 개선 등을 포함하는 업데이트를 지속적으로 제공하는데 이 과정에서 바이너리 파일의 구조가 변경 될 수 있음. 그래서 일반적으로 스토리지 엔진은 한  개 이상의 직렬화 포맷을 지원.  

## 체크섬
디스크에 저장된 파일은 소프트웨어 버그와 하드웨어 장애 등으로 인해 손상될 수 있음. 이런 상황을 사전에 파악하고 손상된 데이터가 다른 서브시스템에 전파되는 것을 방지하기 위해 체크섬과 CRC를 사용.  
데이터를 디스크에 쓰기 전에 체크섬을 미리 계산하고 데이터와 함께 저장. 데이터 요청 시 체크섬을 다시 계산하고 저장된 체크섬과 비교. 값이 일치하지 않는다면 데이터는 손상된 것임.  
파일 전체 에대한 체크섬을 계산하는 것은 비효율적이기 때문에 일반적으로 페이지 단위로 체크섬을 계산하고 페이지 헤더에 저장. -> 체크섬이 더 견고해지고 특정 페이지의 손상을 전체 페이지의 폐기로 이어지지 않게 함.

# 4장. B-트리 구현

## 페이지 헤더
일반적으로 페이지 내용을 나타내는 플래그와 레이아웃, 셀 개수, 빈 공간을 가리키는 하한 및 상한 오프셋과 같은 몇 가지 유용한 메타데이터를 저장.

## 매직 넘버
상수 값을 포함하는 멀티바이트 블록이며 페이지의 종류와 버전과 같은 정보 포함. 검증과 상태 체크에도 사용.

## 형제 링크
좌우에 있는 페이지를 가리키도록 순방향 리크와 역방향 링크를 저장하는 방식으로 트리를 구현하기도 하는데 이렇게 하면 부모 노드를 거슬러 올라가지 않고 이웃 노드를 바로 참조할 수 있다는 장점이 있음. 대신 노드 분할과 병합시 형제 노드의 링크까지 업데이트를 해야한다는 점에서 단점이 있음.

## 가장 오른쪽 포인터
대부분의 구분 키의 구조는 자식 포인터가 있고 마지막 포인터는 어떤 키와도 연관되지 않기 때문에 따로 저장함. 가장 오른쪽 자식 노드가 분할되고 부모에 새로운 셀이 추가되면 부모의 마지막 포인터도 다시 설정해야 함.

## 하이 키
각 트리 노드의 가장 오른쪽 포인터와 노드의 하이키를 함께 저장하는 방법도 있음. 하이 키는 현재 노드의 서브트리에 저장된 가장 큰 키를 나타냄. 이 키는 포인터 Pn이 가리키는 서브트리에서 가장 큰 키를 나타내므로 이 키 값이 해당 서브트리에 저장할 수 있는 최댓값이 됨.  
하이 키를 저장하는 트리는 각 노드에 저장된 키와 포인터의 개수가 같으며, 모든 셀에는 키-포인터 쌍이 존재. 이에 따라 에지 케이스가 줄어들고 가장 오른쪽 포인터의 처리가 단순해짐.

## 오버플로우 페이지
B-트리 알고리즘에서 모든 노드는 일정 개수의 키를 유지해야하는데 각 노드에 저장된 값의 크기가 다를 수 있기 때문에 노드가 가득 찬 상태가 아니지만 이 노드를 저장하는 고정 크기의 페이지에는 남은 공간이 없을 수 있음. 페이지 크기 증가 및 확장은 불가피 하지만 이는 굉장히 비효율적임.  
여러 페이지를 연결하면 데이터를 다른 연속된 공간으로 복사하지 않고 가변 크기 노드를 구현할 수 있음. 이 때 연결 하는 새로 할당된 페이지를 오버플로우 페이지.  
대부분의 B-트리는 고정 크기의 바이트만 노드에 저장하고 나머지는 오브플로우 페이지에 저장. 고정 크기는 노드 크기를 팬아웃으로 나눈 값. 따라서 페이지에 최소 max_payload_byte 바이트만큼의 공간이 항상 남아 있기 때문에 페이지에 공간이 부족한 상황은 발생하지 않음.  
삽입된 데이터가 max_payload_size보다 크다면 해당 노드에 연결된 오버플로우 페이지가 있는지 확인해야 함. 오버플로우 페이지가 존재하고 공간이 충분히 남아 있다면 나머지 바이트를 해당 페이지에 저장. 없다면 새로운 오버플로우 페이지를 할당.  
오버플로우 페이지는 특별 관리가 필요함. 기본 페이지와 마찬가지로 단편화가 발생할 수 있으며, 새로운 데이터를 쓰기 위해 공간을 회수하거나 필요 없는 페이지를 삭제 해야 함.
첫 오버플로우 페이지를 할당할 때에는 해당 페이지의 ID를 기본 페이지의 헤더에 저장함. 오버플로우 페이지가 하나로 충분하지 않아 여러 개가 되는 경우에는 각 헤더 다음 페이지 ID를 저장하고 연결함. 따라서 특정 데이터를 찾기 위해 여러 오버플로우 페이지를 확인해야 할 수 있음.  
키의 카디널리티는 일반적으로 높고 대부분의 경우 기본 페이지에 저장된 키가 비교 대상이기 때문에 키를 나눠서 저장해도 됨.  
데이터 레코드가 요청되면 오버플로우된 부분을 찾아서 반환해야 하지만 일반적으로 이런 요청은 자주 발생하지 않고 만약 모든 데이터의 사이즈가 크다면 블랍 스토리지 등  고려해야 함.

## 이진 검색
트리의 노드에서 특정 키는 이진 검색 알고리즘을 통해 찾을 수 있음. 이진 검색의 특성 상 정렬된 경우에만 유효하기 때문에 키 정렬과 유지가 매우 중요.  
이진 검색 알고리즘은 정렬된 배열과 검색 키를 인자로 받고 숫자를 반환. 반환한 숫자가 양수라면 해당 키는 존재하고 이 값이 배열에서의 위치, 음수면 반환 값이 해당 키의 삽입 위치.  
상위 레벨에서 일치하는 키를 찾는 경우는 드묾. 검색 키보다 큰 첫 번째 값을 찾고 해당 서브트리를 가리키는 포인터를 따라가는 탐색 경로가 중요.

## 간접포인터를 사용한 이진 검색
B-트리 페이지의 셀은 삽입 순서대로 저장되며 셀 오프셋만 논리적 순서를 유지.

## 분할과 병합
B-트리에서 노드의 분할과 병합은 상위 레벨까지 전파될 수 있음. 따라서 분할하는 리프 노드나 병합하는 두 리프 노드부터 루트 노드까지 순회할 수 있어야 함.  
일부 B-트리에서는 노드에 부모 노드를 가리키는 포인터를 저장함. 하지만 하위 레벨의 페이지는 항상 바로 위 레벨을 통해서 참조되기 때문에 부모 노드에 대한 정보는 디스크에 저장하지 않아도 됨.  
형제 포인터와 마찬가지로 부모 포인터도 부모가 변경되면 알맞게 갱신해야 함. 부모 노드의 분할과 병합, 재배치 과정에서 페이지 ID를 포함하는 구분 키가 한 노드에서 다른 노드로 이동했을 때 반드시 갱신해야 함.  
일부 트리 구현에서는 형제 포인터 사용으로 인해 발생할 수 있는 데드록을 제거하기 위해 리프 노드 탐색에 부모 포인터를 사용하기도 함.  
부모 노드에서부터 재귀적으로 포인터를 따라 내려가면 형제 노드를 찾을 수 있고 같은 부모를 공유하는 모든 형제 노드를 순회하고 난 후에는 재귀적으로 상위 레벨로 올라가 검색을 계속함. 그러다 보면 결국 루트 노드에 도달하고 또 다시 리프 레벨까지 내려가게  됨.

## 탐색 경로
부모 포인터를 저장 및 유지하는 대신 리프 노드까지의 경로를 저장해두고 노드 삽입과 삭제로 인해 분할 및 병합이 발생했을 때 저장된 경로를 역순으로 순회하는 방법도 있음.  
B-트리의 구조를 변경하기 위해서는 루트에서 리프 노드 또는 삽입 지점까지 트리를 순회해야 하는데 리프 노드에 도달하기 전에는 분할 또는 병합의 발생 여부를 미리 알 수 없기 때문에 탐색 경로를 저장해야 함.  
탐색 경로는 루트부터 방문한 모든 노드에 대한 정보를 포함. 이러한 정보는 분할 또는 병합이 상위 레벨로 전파될 때 노드를 거슬러 올라가는데 사용.  
노드가 분할되거나 병합되는 경우, 저장된 탐색 경로를 이용해 부모 노드로 승급된 키의 삽입 지점을 찾고 필요하다면 더 상위 레벨 노드까지 차례대로 방문하면서 구조를 변경. 경로를 저장한 스택은 메모리에 유지.  
리프 노드를 분할해야 한다면 스택의 최상위 요소를 참조해 부모 노드를 찾을 수 있음. 부모 노드에 공간이 남아 있다면 탐색 경로에 저장된 셀 인덱스 위치에 새로운 셀을 추가. 만약 공간이 부족하다면 부모 노드도 분할해야 함. 루트 노드에 도달해 스택에 더 이상 요소가 없거나 분할하지 않아도 될 때까지 반복.

## 리밸런싱
일부 B-트리 구현에서는 분할과 병합 비용을 줄이기 위해 레벨 내에서 노드를 리밸런싱하거나 분할 및 병합 작업을 수행하기 전에 상대적으로 빈 공간이 많은 노드로 원소를 이동함. 이 경우 리밸런싱 비용이 높아질 수 있지만 노드의 점유율을 높이고 트리의 높이는 낮출 수 있음.  
노드 삽입과 삭제 시 로드 밸런싱을 수행하는 방법도 있는데 효율적인 공간 활용을 위해 노드를 분할ㄴ 대신 형제 노드로 일부 원소를 옮기고 삽입할 공간을 확보함. 삭제 작업도 마찬가지로 형제 노드와 병합하는 대신 노드가 절반 이상 찬 상태를 유지하도록 형제 노드에서 일부 원소를 가져올 수 있음.  
B*-트리는 형제 노드가 모두 가득 찰 때까지 이웃 노드 간에 원소를 분산하고, 두 노드를 2/3가 채워진 3개의 노드로 분할함. 이 방식은 분할을 지연시켜 평균 점유율을 높일 수 있지만 상태를 관리하고 균형을 맞추는 로직이 추가로 필요. 높은 점유율로 인해 트리 높이가 낮아지고 순회 시 참조하는 페이지 수가 줄어들면 검색 효율성 상승.  
이웃 노드 간 데이터를 분산할 때 노드의 최솟값과 최댓값이 바뀌기 때문에 부모 노드의 키와 포인터를 알맞게 업데이트 해야 함.

## 오른쪽 추가 기법
많은 데이터베이스 시스템에서 자동 증가 값을 기본 인덱스 키로 사용하는데 이방식을 사용하면 모든 삽입이 인덱스 끝에서만 발생하기 때문에 대부분의 노드 분할 작업이 각 레벨의 가장 오른쪽 노드에서 일어나게 됨.

## 벌크 로딩
정렬된 데이터를 벌크 로딩하거나 트리를 재구성할 때에는 우측 추가 알고리즘을 사용할 수 있음. 데이터가 이미 정렬돼 있기 때문에 벌크 로딩 시 트리의 가장 오른쪽에만 데이터를 추가하면 됨.  
이 경우에는 트리를 하위 레벨부터 상향식으로 한 레벨씩 구성하거나, 상위 레벨 노드에 충분한 수의 포인터를 넣을 수 있을 만큼 하위 레벨의 노드가 추가됐을 때 상위 노드를 쓰는 방식으로 트리를 구성하면 노드의 분할과 병합을 피할 수 있음.  
미리 정렬된 데이터를 리프 레벨에 페이지 단위로 저장하는 방식으로 벌크 로딩을 구현할 수도 있음. 리프 페이지 생성 후, 리프 페이지의 첫 번째 키를 부모 노드에 복사하고 상위 레벨은 일반 B-트리 알고리즘을 사용해 구성함. 이 방식도 마찬가지로 데이터가 정렬돼 있기 때문에 노드 분할은 가장 오른쪽 노드에서만 발생.  
B-트리는 항상 최하위 레벨부터 상향식으로 구성하기 때문에 상위 레벨을 만들기 전에 리프 레벨 전체를 먼저 구성할 수 있음. 그렇기 때문에 상위 레벨을 구성하는 시점에는 이미 모든 자식 포인터가 준비돼 있음.  이 방식은 디스크에서 분할이나 병합을 할 필요가 없고 트리를 구성할 때 트리의 최소한의 부분만 메모리에 저장하면 된다는 장점이 있음.  
불변 B-트리도 같은 방식으로 만들 수 있는데, 가변 B-트리와 다르게 수정이 불가능하기 때문에 추가적인 공간 오버헤드가 발생하지 않음. 모든 페이지를 완전히 채울 수 있기 때문에 점유율과 성능이 향상.

## 압축
원시 데이터를 압축하지 않고 저장하면 상당한 저장 오버헤드가 발생할 수 있기 때문에 대부분의 데이터베이스는 공간을 절약할 수 있는 압축 알고리즘을 제공함. 압축 알고리즘에서 접근 속도와 압축률은 서로 상반된 관계. 압축률이 높을수록 데이터 크기는 감소하고 한 번에 더 많은 데이터를 읽을 수 있지만 압축과 압축 해제 작업에서 더 많은 RAM과 CPU 사이클을 사용.  
파일 전체를 압축하면 압축률은 향상하지만 업데이트 시 파일 전체를 다시 압축해야 하기 때문에 비효율적임. 일반적으로 데이터셋이 클수록 작은 압축 단위가 적합. 인덱스 파일 전체를 압축하는 것도 파일 전체를 읽고 압축을 해제해야 하기 때문에 비실용적이며 효율적인 구현 어려움.  
따라서 페이지 단위로 압축. 고정 크기 페이지는 페이지 단위 압축을 사용하기에 알맞음. 페이지는 다른 페이지와 독립적으로 압축 및 압축 해제할 수 있기 때문에 페이지 로딩 및 플러시와 같이 수행할 수 있음. 하지만 일반적으로 데이터 전송이 블록 단위로 이뤄지기 때문에 압축된 페이지가 블록의 극히 일부분을 차지하면 실제 데이터 보다 더 많은 바이트를 읽는 비효율적인 상황이 발생함.  

## 정리와 유지
데이터 무결성 유지와 공간 회수, 오버헤드 최소화, 페이지 정렬등의 다양한 작업이 쿼리 수행과 더불어 수행됨. 이런작업을 백그라운드에서 수행하면 시간을 절약할 수 있으며 삽입과 업데이트, 삭제 작업의 후처리 비용이 줄어듦.  
슬롯 페이지는 설계상 추가적인 페이지 관리가 필요함. 예를 들어 내부 노드의 분할과 병합, 리프 레벨 노드에 대한 삽입 및 업데이트, 삭제 등이 계속 일어나면 단편화가 발생해 논리적 공간은 충분하지만 연속된 물리적 공간이 부족한 페이지가 발생.  
B-트리는 루트 노드에서부터 탐색을 시작. 탐색 경로를 따라 접근할 수 있는 데이터를 라이브(addressable) 상태라고 함. 참조맣ㄹ 수 없는 데이터는 가비지라고 하며 어디에서도 참조하지 않고 읽을 수 없기 때문에 null값과 같음.  

## 업데이트와 삭제로 인한 단편화
삭제된 리프 레벨의 셀은 헤더에서 오프셋만 제거하고 실제 셀은 남겨둠. 해당 셀은 더 이상 참조할 수 없으며 관련 데이터는 쿼리 대상에서 제외. 따라서 null 처리하거나 이웃 셀을 이동하지 않아도 됨.  
페이지가 분할되면 페이지의 일부는 더 이상 참조할 수 없기 때문에 해당 오프셋은 삭제. 삭제된 오프셋의 셀은 새로운 데이터로 덮어쓰거나 정리 단계에서 가비지 컬렉터가 처리.  
삭제된 셀의 오프셋만 삭제하고 다른 셀을 재배치하거나 공간 확보를 위해 물리적으로 셀을 삭제하지 않기 때문에 사용 가능한 바이트가 페이지에 흩어져 있을 수 있는데 이를 단편화(fragmentation)라고 하며, 제거해야 하는 현상임.  
일반적으로 데이터를 삽입하려면 셀 크기에 맞는 연ㄴ속된 바이트 블록이 필요하고 단편화된 여러 조각을 모아 연속된 공간을 확보하려면 페이지를 재구성해야 함.  
삽입 작업은 튜픙르 삽입 순서대로 저장. 큰 차이는 없지만 튜플을 논리적 순서대로 저장하면 캐시를 프리페치해 순차 읽기에 도움이 될 수 있음.  
내부 페이지의 키는 탐색 경로를 안내하는 이정표 역할을 하며 서브트리의 범위를 정의할 뿐임. 따라서 업데이트 작업은 대부분 리프 레벨에서 수행됨. 또 업데이트 작업은 키 단위로 수행되며, 오버플로우 페이지 생성 이외의 트리의 구조를 변경하는 작업은 수행하지 않음. 리프 노드 업데이트 시, 페이지 재구성을 최소화하기 위해 셀 순서는 변경하지 않고, 따라서 셀의 여러 버전이 존재할 수 있고 이 가운데 한 개의 버전만 접근할 수 있음.

## 페이지 단편화
공간 회수 및 페이지를 재구성하는 과정을 컴팩션, 정리 또는 유지보수라고 함. 페이지에 사용 가능한 물리적 공간이 부족한 경우 컴패션과 쓰기를 동시에 수행할 수 있음. 하지만 일반적으로 컴팩션은 페이지별로 가비지 컬렉션을 수행하고 데이터를 재작성하는 독립적인 비동기적 과정을 말함.  
컴팩션은 데드 셀이 차지하는 공간을 회수하고 셀을 논리적 순서로 재정렬함. 재구성된 페이지는 파일에서의 위치가 변경될 수 있고 사용 중이지 않은 인메모리 페이지는 사용 가능 상태로 변경되며 페이지 캐시에 반환됨. 디스크에 새로 할당된 페이지의 ID는 프리 페이지 목록에 추가. 이 목록은 사용 가능한 공간이 누락되거나 낭비되지 않도록 노드 장애나 재부팅 시에도 유지돼야 함.

# 5장. 트랜잭션 처리와 복구
트랜잭션이란 하나의 논리적 작업 단위를 의미하며 여러 작업을 한 단계로 표현하는 방법. 작업은 데이터베이스의 읽기와 쓰기를 모두 포함. 모든 데이터베이스 트랜잭션은 원자성과 일관성, 격리성, 지속성을 보장. -> ACID.  
- 원자성(Atomicity): 트랜잭션을 더 작은 단계로 나눌 수 없음. 트랜잭션과 관련된 작업은 모두 실행되거나 모두 실패해야 함. 부분적으로 실행 X. 커밋되든지, 실패하든지. 커밋은 트랜잭션의 마지막 단계. 실패한 트랜잭션은 재시도할 수 있음.
- 일관성(Consistency): 일관성은 애플리케이션이 제어하는 속성. 트랜잭션은 참조 무결성 등의 제약 조건을 위반하지 않고 데이터베이스를 하나의 유효한 상태에서 또 다른 유효한 상태로 변경. 일관성은 가장 약하게 정의된 성질로, 데이터베이스가 아닌 사용자가 제어할 수 있는 유일한 속성.
- 격리성(Isolation): 동시에 수행되는 여러 트랜잭션은 서로 간섭 없이 수행돼야 함. 격리성은 수정 내용이 반영되는 시점과 동시 수행 중인 트랜잭션이 접근할 수 있는 데이터를 정의. 많은 데이터 베이스는 성능상의 이유로 약한 격리 수준(Isolation Level)을 사용. 동시성 제어 방식에 따라 트랜잭션의 변경 내용 중 일부가 동시 수행 중인 다른 트랜잭션에 노출될 수도 있고 노출되지 않을 수도 있음.
- 지속성(Durability): 트랜잭션 커밋 후 디스크에 저장된 데이터베이스의 상태는 시스템이 중단 되거나 정전 또는 시스템 장애가 발생해도 유지돼야 함.  
트랜잭션 매니저는 트랜잭션의 세부 단계를 제어, 관리 및 스케줄링하는 컴포넌트.  
잠금 매니저는 리소스에 대한 동시 접근을 제어하고 데이터 무결성 보장. 잠금이 요청되면 잠금 매니저는 다른 트랜잭션이 공유 혹은 배타적 잠금 모드로 해당 리소스를 이미 소유하고 있는 지 확인. 요청자가 해당 리소스에 대한 접근 권한이 있다면 접근을 허용. 배타적 잠금은 동시에 한 개의 트랜잭션만이 소유할 수 있기 때문에 다른 트랜잭션은 잠금이 해제될 때까지 기다리거나 중단 후 나중에 재시도해야 함. 잠금이 해제되거나 트랜잭션이 완료되면 잠금매니저는 대기 중인 트랜잭션에 알림.  
페이지 캐시는 디스크와 스토리지 엔진 사이에서 중개자 역할을 함. 메인 메모리의 변경 사항을 저장하고 디스크와 동기화 되지 않은 페이지를 캐시. 모든 데이터베이스 상태에 대한 변경 사항은 우선 페이지 캐시에 저장됨.  
로그 매니저는 디스크와 동기화되지 않은 페이지 캐시의 내용이 손실되지 않도록 작업 히스토리 저장. 로그를 기반으로 부팅 시 작업을 재수행하고 마지막 캐시 상태 재구성. 중단된 트랜잭션이 변경한 내용을 언두할 때에도 로그 사용.

## 버퍼 관리
대부분의 데이터베이스는 상대적으로 속도가 느린 디스크와 빠른 메인 메모리로 구성된 메모리 계층 구조로 돼 있기 때문에 디스크 접근 횟수를 줄이기 위해 페이지를 메모리에 캐시하고 스토리지 계층에서 캐시된 페이지를 재요청하면 캐시에서 반환함.  
다른 프로세스가 디스크에 저장된 같은 페이지를 변경하지 않았다면 메모리에 캐시된 페이지를 재사용할 수 있음. -> 가상 디스크(Virtual disk). 가상디스크 읽기 작업은 요청된 페이지가 메모리에 없을 경우에만 물리적 저장소에 접근. 더 일반적인 명칭은 페이지 캐시 또는 버퍼 풀. 페이지 캐시는 디스크에서 읽은 페이지를 메모리에 캐시. 시스템 장애가 발생하거나 시스템이 비정상적으로 종료되면 캐시된 데이터는 삭제.  
페이지 캐시는 데이터베이스에서만 사용되는 개념이 아니고 운영체제도 I/O 시스템 호출(Syscall)의 성능을 높이기 위해 디스크에 저장된 내용을 비어 있는 메모리 세그먼트에 캐시함.  
아직 캐시되지 않은 페이지를 디스크에서 메모리로 복사하는 작업을 페이징이라고 함. 아직 디스크로 플러시되지 않은 변경된 페이지는 더티 페이지라고 표현.  
일반적으로 페이지 캐시의 메모리 영역은 전체 데이터셋보다 작기 때문에 이 영역은 결국 모두 사용될 것이고 새로운 페이지를 추가하기 위해 기존 페이지를 만료시켜야 함.  
페이지 캐시는 순서를 고려하지 않고 페이지를 빈 슬롯에 복사하기 때문에 디스크와 메모리에 페이지가 정렬되는 방식 사이에는 연관성이 없음.  
페이지 캐시의 주요 기능  
- 페이지 내용을 메모리에 캐시
- 디스크에 저장된 페이지에 대한 변경 사항을 함께 버퍼링하고 캐시된 페이지에 반영
- 캐시되지 않은 데이터가 요청된 경우 메모리에 공간이 충분하다면 페이징하고 캐시된 버전을 반환
- 캐시된 페이지가 요청된 경우 메모리에서 반환
- 메모리에 새로운 페이지를 추가할 공간이 없을 경우 일부 페이지를 만료시키고 디스크로 플러시

## 캐싱
버퍼링에 대한 변경 사항은 디스크에 쓰기 전까지 메모리에 남겨둠. 어떤 프로세스도 원본 파일을 수정할 수 없기 때문에 동기화는 메모리에서 디스크로 플러시하는 단방향 작업임. 데이터베이스는 페이지 캐시를 사용해 메모리를 관리하고 디스크 접근을 제어. 페이지 캐시를 애플리케이션에 특화된 커널 페이지 캐시라고 생각할 수 있음. 블록 디바이스에 바로 접근하고 기능 및 목적이 커널 페이지와 유사함. 나아가 디스크 접근을 추상화하고 논리적 쓰기와 물리적 쓰기를 분리함.  
페이지를 캐시하면 알고리즘을 수정하거나 객체를 메모리에 실체화하지 않고 트리의 일부를 메모리에 저장할 수 있음. 간단하게 디스크에 접근하는 대신 페이지 캐시를 요청하면 됨.  
스토리지 엔진이 특정 페이지를 요청하면 우선 캐시된 버전이 있는지 확인하고 있을 경우 반환. 없다면 논리적 페이지 주소 또는 페이지 번호를 물리적 주소로 변환해 해당 페이지를 메모리에 복사하고 반환. 이때 해당 페이지가 저장된 버퍼는 참조 상태라고 표현하고 작업이 끝나면 스토리지 엔진은 해당 페이지를 페이지 캐시에 반환 또는 참조 해제 해야 함. 페이지를 고정 시키면 페이지 캐시에서 제거되지 않음.  
페이지가 변경된 경우에 페이지에 더티 플래그를 설정. 더티 플래그는 해당 페이지가 디스크와 동기화되지 않았고 지속성을 위해 디스크로 플러시돼야 한다는 것을 의미.

## 캐시 만료
캐시된 데이터가 많을수록 더 많은 읽기 요청을 디스크에 접근하지 않고 처리할 수 있음. 나아가 같은 페이지에 대한 변경 사항을 더 많이 같이 버퍼할 수 있음. 하지만 페이지 캐시의 크기는 한정적이기 때문에 새로운 페이지를 저장하기 위해 오래된 페이지는 제거해야 함. 이때 페이지가 동기화됐고(플러시 또는 수정 X) 고정 또는 참조 상태가 아니라면 바로 제거 가능. 더티 페이지는 제거되기 전에 먼저 플러시해야 함. 참조 상태의 페이지는 사용이 끝나기 전까지는 제거될 수 없음.  
페이지를 제거할 때마다 디스크로 플러시한다면 성능을 저하시킬 수 있기 때문에 일부 데이터베이스는 별도의 백그라운드 프로세스가 제거될 가능성이 높은 더티 페이지를 주기적으로 디스크로 플러시함.  
지속성은 데이터베이스에서 매우 중요한 속성. 데이터베이스에 장애가 발생하면 플러시 되지 않은 데이터는 손실되기 때문에 데이터 손실을 방지하기 위해 체크포인트 프로세스가 플러시 시점을 제어함. 체크포인트 프로세스는 선행 기록 로그(WAL)와 페이지 캐시의 싱크가 맞도록 조정함. 오직 플러시가 완료된 캐시된 페이지와 관련된 로그만 WAL에서 삭제될 수 있음. 이 과정이 완료될 때까지 더티 페이지는 제거 X.  
캐싱에서 발생하는 여러가지 트레이드-오프  
- 디스크 접근 횟수를 줄이기 위해 플러시 시점을 늦춤.
- 페이지를 우선적으로 플러시해 빠르게 캐시에서 제거.
- 제거할 페이지를 선택하고 최적의 순서로 플러시.
- 캐시 크기를 메모리 범위 내로 유지.
- 기본 저장소에 저장되지 않은 데이터는 손실되지 않아야 함.

## 페이지 고정
